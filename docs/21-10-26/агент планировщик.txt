Интеграция OpenAI Deep Research через коннекторы приложений (app://connector) реализуется с помощью четырехкомпонентной агентной архитектуры, работающей поверх протокола Model Context Protocol (MCP). Основная задача такого коннектора — дать автономному ИИ-исследователю безопасный и структурированный доступ к закрытым корпоративным данным (Google Drive, GitHub, Slack, Notion) или локальным базам данных взамен стандартного поиска в публичном интернете. 
OpenAI Developers +3
Ниже подробно описан сквозной пайплайн (жизненный цикл) работы этого механизма.
Архитектура пайплайна (4-Agent Architecture)
Внутри экосистемы OpenAI процесс разбивается на параллельное и последовательное взаимодействие четырех специализированных агентов: 
OpenAI Developers

    Triage Agent (Агент сортировки): Принимает верхнеуровневый запрос от пользователя, определяет необходимость привлечения внешних коннекторов и планирует, к каким именно приложениям (через MCP) нужно обратиться. 
    OpenAI Developers
    Clarifying Questions Agent (Агент уточнения): Работает на легкой модели (например, gpt-4o-mini). Он запрашивает у пользователя недостающий контекст, ограничения и специфику бизнес-логики до начала исследования. 
    OpenAI Developers
    Research Instruction Agent (Агент обогащения промпта): Переводит «сырой» диалог и уточнения пользователя в детальный исследовательский бриф (Research Brief), который служит дорожной картой для глубокого поиска. 
    LangChain +1
    Research Agent (Основной агент): Работает на мощных рассуждающих (reasoning) моделях (таких как gpt-5.6-sol или специализированная o3/o4-mini). Именно этот агент непосредственно дергает инструменты подключенного MCP-сервера в многопоточном режиме. 
    OpenAI Developers +1

Этапы работы пайплайна коннектора
Этап 1. Инициализация и авторизация (OAuth 2.1)

    Пользователь активирует режим Deep Research в интерфейсе и выбирает в качестве источника подключенное приложение. 
    GitHub +1
    Происходит проверка токенов доступа. Подключение кастомных коннекторов к ChatGPT выполняется по протоколу OAuth 2.1 с механизмом PKCE (S256). 
    Profitec AI
    Важно: ИИ строго наследует права доступа (ACL) авторизованного пользователя. Он не увидит те документы компании, к которым у данного сотрудника нет доступа в исходной системе. 
    HubSpot Developers +1

Этап 2. Формирование поисковой стратегии

    Основной исследовательский агент декомпозирует сложную задачу на десятки мелких подзадач. На основе созданного брифа он генерирует специфичные поисковые запросы, оптимизированные под структуру целевого приложения (например, под синтаксис поиска в Jira, Notion или базах данных).

Этап 3. Исполнение циклов через интерфейсы search и fetch
Для взаимодействия с коннектором модель использует строго фиксированную сигнатуру Read-Only инструментов (запись и изменение данных в режиме исследования запрещены в целях безопасности): 
OpenAI Help Center +2

[Поисковый запрос] ➔ (Инструмент: search) ➔ Возвращает список [{id, title, url}]
                                                    │
  ┌───────────────── Сбор метаданных ───────────────┘
  ▼
[Анализ кандидатов] ➔ (Инструмент: fetch)  ➔ Возвращает тело {id, title, text, url, metadata}

    Инструмент search(query): Агент отправляет поисковый запрос в коннектор. Сервер приложения обязан вернуть массив объектов, содержащих уникальный id документа, его заголовок title и url. 
    ai-flip.ru
    Фильтрация и приоритизация: Модель оценивает релевантность полученных метаданных.
    Инструмент fetch(id): Для наиболее подходящих документов агент вызывает метод fetch, который извлекает уже полный текстовый массив (text), структуру и расширенные метаданные (metadata). 
    ai-flip.ru

Этап 4. Автономное рассуждение, ветвление и адаптация (Reasoning & Python Tool)

    Получив данные из коннектора, модель анализирует их. Если в документах обнаруживаются новые сущности или пробелы, агент адаптирует план на лету, возвращается на Этап 3 и делает новые, более точечные запросы через коннектор (Backtracking).
    При необходимости агент может писать и исполнять изолированный Python-код для анализа таблиц, сопоставления графиков или калькуляции финансовых метрик, извлеченных из приложения.
    Временные рамки: Весь этот итеративный цикл может занимать от 5 до 30 минут (в зависимости от глубины и объема данных). Прогресс шагов стримится пользователю в реальном времени. 
    OpenAI +5

Этап 5. Синтез и генерация отчета с цитированием

    После завершения поисковых циклов вся собранная информация агрегируется.
    Агент формирует итоговый структурированный отчет (длиной до десятков страниц).
    Пайплайн требует обязательного наличия непустого url в данных коннектора. На их основе ИИ расставляет автоматические строгие цитаты (citations), чтобы пользователь мог кликнуть на утверждение в отчете и сразу перейти к конкретному файлу или ветке внутри своего рабочего приложения. 
    Reddit·r/LLMDevs +2

    Ограничение времени хранения: В фоновом режиме работы (Background mode) данные, полученные через коннекторы, кэшируются на стороне OpenAI всего около 10 минут, после чего уничтожаются.

более подробно об устройстве расскажи по шагам
Чтобы детально понять, как устроен пайплайн OpenAI Deep Research при работе через коннекторы приложений (app://connector), нужно заглянуть под капот ИИ-движка. Этот процесс кардинально отличается от работы обычного ChatGPT, так как здесь модель переходит от концепции «генерации текста» к концепции «автономного планирования и выполнения кода».
Ниже представлен подробный пошаговый разбор технического устройства пайплайна на каждом этапе его жизненного цикла.
Шаг 1. Инициализация и построение Графа Задачи (Task Graph)
Как только пользователь отправляет запрос (например: «Проанализируй архитектурные долги в нашем GitHub-репозитории X и сопоставь с жалобами клиентов в Slack за последний месяц»), запускается Triage Agent.

    Семантический парсинг: Модель анализирует синтаксис app://connector и определяет, к каким именно манифестам и API-ключам подключенных сервисов (GitHub и Slack) у нее есть доступ.
    Построение дерева целей (Goal Decomposition): Вместо генерации прямого ответа модель создает направленный ациклический граф (DAG). Задача разбивается на подцели:
        Цель А: Собрать открытые Issue и Pull Requests с тегом tech-debt.
        Цель Б: Выгрузить логи каналов поддержки в Slack.
        Цель В: Сопоставить ключевые слова и выявить корреляцию.
    Оценка токенов и контекста: Модель рассчитывает лимиты контекстного окна (Context Window Budget) для каждой ветки, чтобы не перегрузить систему огромными файлами.

Шаг 2. Адаптивное уточнение контекста (Pre-Flight Clarification)
До отправки первых запросов к API в работу включается Clarifying Questions Agent. Его задача — минимизировать холостые (и дорогие) циклы рассуждений модели.

    Поиск неопределенностей: Модель сканирует граф задачи на наличие «белых пятен». Например: «В Slack 500 каналов, в каких именно искать? За какой период брать данные из GitHub?»
    Генерация динамической формы: Пользователю выводится лаконичный список вопросов.
    Обновление системного промпта: Ответы пользователя упаковываются в строго структурированный JSON-бриф (Research Brief), который намертво прикрепляется к контексту основного рассуждающего агента (Research Agent) в качестве наивысшего приоритета.

Шаг 3. Итеративный цикл поиска (The MCP Execution Loop)
Это ядро системы. Модель использует рассуждения (Reasoning Tokens), имитируя мышление человека перед выполнением каждого действия. Шаг повторяется циклически (до 50–100 раз за исследование).
Каждая итерация внутри цикла делится на микро-шаги:

[Мышление (Thought)] ➔ [Выбор Инструмента] ➔ [Вызов API] ➔ [Анализ Результата (Observation)]
        ▲                                                                │
        └────────────────────────── Повтор цикла ────────────────────────┘

    Thought (Внутреннее рассуждение): Модель генерирует скрытые от пользователя рассуждения. «Мне нужно найти упоминания модуля авторизации. Сначала я вызову метод search в коннекторе Slack с фильтром по дате».
    Call (Вызов инструмента): Модель генерирует стандартизированный вызов к MCP-серверу (Model Context Protocol):
    json

    {
      "method": "tools/call",
      "params": {
        "name": "app_connector_slack_search",
        "arguments": {
          "query": "auth-module failed",
          "limit": 20
        }
      }
    }

    Используйте код с осторожностью.
    Execution & Scrape (Исполнение коннектором): Коннектор переводит этот вызов в нативный запрос к API Slack, забирает данные, очищает их от лишнего JSON-мусора (оставляя только текст, ID и URL) и возвращает модели текстовый блок (Observation).
    Fetch (Углубление): Если в результатах search модель видит важный документ (например, файл auth_handler.py), она вторым шагом вызывает fetch(file_id), чтобы прочитать его код целиком.

Шаг 4. Возврат по цепочке рассуждений (Backtracking & Pivot)
Обычные LLM идут строго вперед. Пайплайн Deep Research умеет признавать ошибки и менять курс.

    Критика результатов: Получив код из коннектора, модель сопоставляет его со своей базой знаний. Если код написан на незнакомом внутреннем фреймворке, она фиксирует: «Информации недостаточно, изначальный поисковый запрос был неверным».
    Тупиковые ветви (Pruning): Модель «отрезает» неэффективные ветки графа задач, чтобы не тратить лимиты.
    Изменение стратегии (Pivot): Модель генерирует совершенно новые поисковые запросы. Например, вместо поиска по слову «ошибка» она начинает искать фамилию автора этого модуля в логах Jira через другой коннектор.

Шаг 5. Аналитическая обработка во внутреннем Sandbox (Python-слой)
Когда сырые данные из коннекторов собраны, их нужно обработать. Модель не делает аналитику «на глаз».

    Генерация скрипта: Если модель скачала из коннектора (например, из Google Drive) тяжелую CSV-таблицу с логами ошибок, она пишет Python-скрипт для ее обработки.
    Изолированное выполнение: Код запускается в защищенном контейнере (Sandbox) на серверах OpenAI. Скрипт строит матрицы корреляции, агрегирует данные по дням или фильтрует дубликаты.
    Чтение вывода: Модель анализирует только текстовый или табличный вывод (stdout) работы этого скрипта, внедряя точные цифры в свой будущий отчет.

Шаг 6. Синтез отчета, кросс-верификация и линковка (Citations Engine)
Финальный этап, на котором хаотичный набор скачанных данных превращается в документ.

    Сборка черновика (Drafting): Модель формирует структуру отчета. Каждый ключевой вывод подкрепляется фактом из шага №3 или №5.
    Кросс-верификация (Fact-Checking): Внутренний под-агент проверяет, не придумала (галлюцинировала) ли модель цифры. Он сверяет итоговый текст с исходными данными, которые вернул инструмент fetch.
    Простановка постоянных ссылок (Deep Linking): Система жестко связывает текст отчета с источниками. Для каждого утверждения из метаданных коннектора извлекается url. В итоговом Markdown-файле это превращается в кликабельные сноски: [1](https://github.com). Если пользователь нажмет на нее, он попадет ровно на ту страницу в корпоративной сети, откуда ИИ взял информацию.

Для того чтобы описать устройство этой системы на уровне системной архитектуры, абстрагируемся от конкретных сервисов (вроде Slack или GitHub). В основе работы Deep Research через коннекторы лежит строгое математическое и программное моделирование: пространство состояний, контракты данных и динамический контекст.
Ниже представлен детальный разбор устройства пайплайна в виде обобщенного шаблона, типов сущностей и структуры контрактов взаимодействия (в формате, близком к Model Context Protocol / OpenAPI).
1. Архитектурные Сущности (Entities)
На протяжении всего жизненного цикла система оперирует четырьмя типами абстрактных сущностей:

    Агент-Планировщик (Orchestrator / Router): Высшая сущность (LLM с большим контекстом), которая не выполняет работу сама, а строит граф, распределяет бюджет токенов и валидирует результаты.
    Исполнительный Агент (Worker / Tool-User): Специализированный контекстный поток (LLM с низким latency и высокой точностью генерации кода/параметров), оптимизированный под цикл Thought
    Action
    Observation.
    Коннектор (Connector / MCP Server): Изолированный программный модуль (Proxy), который переводит абстрактные контракты ИИ в нативные протоколы внешнего мира и обратно. Коннектор «глуп» — он не знает о целях исследования, он лишь выполняет декларативные команды и возвращает строго структурированные данные.
    Артефакт (Artifact): Неизменяемая (immutable) сущность, рождающаяся в процессе исследования (скачанный файл, сгенерированный датафрейм, промежуточный вывод). Артефакты складываются во внутреннее хранилище (Blob Storage / Vector DB) и индексируются.

2. Динамический Контекст и Переменные (Context & State Variables)
Контекст модели — это не просто текст, это динамическая структура данных, которая постоянно пересобирается. Переменные внутри контекста делятся на три слоя:

┌────────────────────────────────────────────────────────┐
│ ГЛОБАЛЬНЫЙ СТАТИЧЕСКИЙ КОНТЕКСТ (Иммутабельный)        │
│ ── Вводная задача, Бриф пользователя, Границы (Scope)   │
├────────────────────────────────────────────────────────┤
│ ДИНАМИЧЕСКОЕ СОСТОЯНИЕ (Мутабельное)                   │
│ ── Текущий узел графа tasks[i], Доступные токены       │
├────────────────────────────────────────────────────────┤
│ ЛОКАЛЬНЫЙ КОНТЕКСТ ИТЕРАЦИИ (Временный)                │
│ ── Результат последнего вызова (Observation), Логи     │
└────────────────────────────────────────────────────────┘

Системные переменные, удерживаемые в памяти:

    $global_budget_tokens: Общий лимит на исследование (например, 10,000,000 токенов рассуждения). При приближении к 0 запускается аварийный алгоритм сворачивания и синтеза того, что есть.
    $task_graph_state: JSON-дерево, где каждый узел имеет статус: [Pending, Processing, Completed, Failed, Abandoned].
    $knowledge_registry: Индекс всех загруженных во внутреннюю память артефактов с их метаданными (ID, Hash, Source-URI).

3. Контракты Взаимодействия (Schemas & API Contracts)
Связующим звеном между ИИ и внешним миром выступают декларативные контракты. Модель видит коннектор не как код, а как схему возможностей (Capabilities Scheme).
Контракт А: Регистрация коннектора (Интроспекция)
Когда коннектор подключается к системе, он передает свою схему (обычно по протоколу JSON-RPC / MCP).
json

{
  "connector_id": "app_connector_generic_v1",
  "capabilities": {
    "resources": [
      {
        "uri_template": "app://connector/space/{space_id}/entity/{entity_id}",
        "description": "Прямой доступ к атомарному объекту системы в рамках пространства имен",
        "mime_type": "application/json"
      }
    ],
    "tools": [
      {
        "name": "query_index",
        "description": "Поиск объектов по текстовым маркерам и мета-фильтрам",
        "input_schema": {
          "type": "object",
          "properties": {
            "query": {"type": "string"},
            "filters": {
              "type": "object",
              "properties": {
                "created_after": {"type": "string", "format": "date-time"},
                "status": {"type": "string"}
              }
            },
            "limit": {"type": "integer", "default": 20}
          },

        }
      },
      {

Контракт Б: Вызов Инструмента (Запрос от ИИ)
Когда Исполнительный Агент в цикле рассуждения решает сделать шаг, он генерирует строго валидный JSON, соответствующий схеме выше:
json

{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "query_index",

4. Типовой Шаблон Выполнения (Execution Step Template)
Каждый шаг внутри исследовательского цикла можно разложить на выполнение следующего псевдокода на стороне ИИ-платформы:
python

def execute_research_step(current_task):
    # 1. Формирование контекста итерации
    context = assemble_context(
        global_brief, 
        current_task.goal, 
        registry=knowledge_registry
    )
    
    # 2. Генерация токенов рассуждения (Thought) и выбор действия
    # Модель «думает» и выдает структурированную команду tool_call
    thought, tool_call = reasoning_llm.generate(context)
    log_thought(thought) 
    
    # 3. Валидация контракта на стороне платформы
    if not validate_json_schema(tool_call, connector.schema):
        # Если модель ошиблась в синтаксисе, возвращаем ей ошибку как Observation
        return handle_syntax_error(tool_call)
        
    # 4. Исполнение через Коннектор (Слой абстракции)
    try:
        raw_response = connector.dispatch(tool_call)
        observation = normalize_response(raw_response)
    except Exception as e:
        observation = {"error": str(e), "type": "RuntimeError"}
        
    # 5. Мутация состояния (State Mutation)
    if "error" not in observation:
        # Регистрируем новые URI для последующего цитирования
        knowledge_registry.register(observation.meta)
        current_task.update_status("Processing")
    else:
        # Включается алгоритм Backtracking (модель в следующем шаге увидит ошибку и изменит параметры)
        current_task.register_attempt_failure()
        
    return observation

Используйте код с осторожностью.
Главный вывод
Устройство Deep Research строится на изоляции ответственности: ИИ отвечает исключительно за логику переходов по графу задач, семантический анализ текстов и генерацию параметров по схемам. Коннектор отвечает исключительно за транспорт, авторизацию во внешней системе и приведение проприетарного API к единому мета-контракту.
