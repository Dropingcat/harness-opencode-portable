# A2: реальные сценарии передачи находок

**Задача:** TD-185 / HARNESS-A2-REAL-TRANSFER-20261016. **Статус:** OPEN / NOT_TESTED. Регистрация задачи не является запуском сценариев или отменой принятого code-only внедрения A2.

## Зачем отдельная приёмка

A2 установлен в каноническое дерево; 69 fixture-методов прошли в worktree, staging и копии установленного кода. Это доказательства компонентов, но не реальной передачи через OpenCode и исполняемые границы наблюдатель → корзина → планировщик → потребитель. Настоящий поток и его причины отказа ещё не сертифицированы. Качество семантических эвристик аудитора и nested-dispatch — отдельные вопросы.

**Область архитектуры:** W6 — хостовые сессии/передача, W7 — наблюдение/корзина/планирование, W13 — доказательства и приёмка. Связи: TD-179, TD-184, TD-RESTORE-01; следующий потребитель — A3. Реестр TD остаётся каноническим config/tech_debt.json.

## Два уровня, не взаимозаменяемых

1. **Реальный межпроцессный путь компонентов:** отдельные процессы производителя, читателя и подтверждающего потребителя используют установленные модули A2, явные sandbox-пути и настоящий обмен через файлы. Без AST-extract, подмены DamageBasket/планировщика/ack и заранее подставленного результата потребителя.
2. **Хостовый handoff OpenCode:** контролируемый безвредный артефакт действительно передаётся между разрешёнными сессиями/ролями через поддерживаемый интерфейс, затем в реальный поток компонентов. Записываются фактические session/agent/model/provider/parentID, версии host/контракта, пути импорта и хеши артефактов. Передача текста только в описании роли не считается выполненной передачей.

Уровень 1 не закрывает уровень 2. При TD-184 требование настоящего nested-child возвращает BLOCKED; standalone-режим маркируется именно так и не закрывает TD-184. Если выбранный хостовый маршрут недоступен, фиксировать отказ, не заменять его general или фиктивной квитанцией. Действующее A2 CLI-исключение не переносится автоматически на A3.

## Матрица сценариев

| ID | Реальная последовательность | Приёмка |
|---|---|---|
| R1 | Безвредный артефакт → существующий наблюдатель → запись → другой процесс читает/планирует | Стабильные finding/event ID, исходное время, точное содержимое и сумма damage; фактический импорт canonical A2, один согласованный снимок |
| R2 | Повторная доставка **того же** события после перезапуска производителя/читателя | ID/time/payload неизменны, дополнительный damage не начислен; новый random-ID не выдаётся за retry |
| R3 | Два реальных производителя и реальный читатель, барьер и контролируемое перекрытие | Ни одна запись не потеряна; результаты чтения привязаны к наблюдаемому снимку, не к обещанию единого глобального момента |
| R4 | Потребитель захватывает снимок, другой процесс добавляет находку, первый подтверждает снимок | Поздняя находка остаётся; история подтверждений сохраняет исходные ID/payload и связь со снимком |
| R5 | Процесс потребителя завершается до/после ack, затем повторяет доставку/ack | Нет потери/воскрешения находок, повтор безопасен; проверка относится к ack A2, не exactly-once внешнего исправления A3 |
| R6 | Коллизия ID, чужой/повреждённый снимок, неправильная форма данных, lock deadline, сбой замены | Явный наблюдаемый отказ; прежние данные сохраняются; нет пустого успешного результата или частичного batch |
| R7 | Host handoff: отмена, отсутствующий tool/target, отсутствующий/невалидный выход, cold start и две параллельные цепочки | Нет молчаливого fallback; артефакты и сессии не смешиваются; причины BLOCKED/FAIL/NOT_TESTED видимы |
| R8 | Host handoff → реальный producer/consumer → повторное чтение после рестарта | Корреляция сохраняется от session/run до finding/snapshot/ack; фактическое состояние подтверждается независимым читателем |

R1 может использовать детерминированный наблюдатель с заранее известным дефектом синтетического артефакта; это не оценка качества LLM-аудита. Внешний аудитор B наблюдает, а не исправляет. Процессный аудитор A оценивает процесс, а не валидирует собственный код.

## Изоляция и границы разрешений

- Все state/basket/receipt-пути явно находятся в отдельном временном workspace. Установленные модули используются как код, не как разрешение писать production-default paths.
- Нет запуска production daemon/MetaCore/bootstrap/nightly, реального sleep/merge/HP/reward, TD updater, памяти или самообучения. Для одних только ack-тестов не требуется имитировать «исправление принято» в производстве.
- Только текущий OpenAI через OpenCode в отдельно разрешённом host-canary; без Polza, установки SDK, извлечения OAuth, секретов в argv или журналирования настоящих документов.
- Любая запись в реальную корзину либо активация фоновых процессов требует отдельного сценарного разрешения и контролируемого окна. Этим документом такие действия не разрешены.
- Дедлайны и finally cleanup дочерних процессов обязательны; принудительная остановка допускается только для собственных sandbox-детей с подтверждённой идентичностью.

## Выход и закрытие

До исполнения подготовить версионированный runnable-контракт сценариев, входные хеши, ожидаемые инварианты, отрицательные контроли и бюджет. Для каждого сценария: команда/маршрут, host/version/agent identity, source hash/import root, события со связью run/session → event → finding → snapshot → ack, наблюдаемое состояние, exit/status/error и следы отмены/cleanup. Логи без секретов; настоящий payload не сохраняется в общем журнале.

Независимые tester/reviewer принимают фактические результаты; code-only A2 статус не переписывается в host-E2E PASS. TD-185 закрывается только после успешных обоих уровней на заявленном маршруте и фиксации ограничений. Недоступный nested-маршрут остаётся BLOCKED по TD-184, а не «условно успешным». Срок: до заявления о сквозной host-интеграции A2 и до допуска A3 к рабочему ack/восстановлению. Планирование и sandbox-разработка A3 могут идти параллельно.
