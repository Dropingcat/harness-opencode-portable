## 1. Место в существующей архитектуре

Сохраняется цепочка: W5 route/bundle → W6 координация и host-handoff → W7 наблюдение/план сна → W13 изолированные изменения/проверки → принятый результат. А1 хранит историю и транзакции; А2 хранит находки и подтверждает точный снимок. **А3 определяет, когда результат действительно принят и какие последствия разрешены.**

Аудитор B наблюдает объект и выдаёт находки, не исправляет и не принимает собственный фикс. Reviewer проверяет код, аудитор A — процесс по метаданным. Планировщик выбирает работу, но не выдаёт исполнителю дополнительные права. Наличие route, расписания, Git merge, красивого отчёта или высокого XP не доказывает исправление.

Источники: исходный план A1–A6, текущий архитектурный обзор, оригиналы канона ch19–24/ch26–29, CODERS02/14/21. ## 3. Противоречие и выбранный подход

**Противоречие:** больше автоматического восстановления повышает скорость, но при слабой приёмке создаёт ложный успех и повторные эффекты. **ИКР:** все входы сна имеют один доказанный исход; неподтверждённый результат не изменяет принятого состояния и не закрывает находки.

Рассмотрены три совместимых концепции: общий гейт, публикация копии состояния, возобновляемая финализация. Выбирается их узкая композиция, не новый workflow framework. Принципы: посредник (24) между свидетельством и эффектами; предварительная защита (11); разделение по условию/во времени. Существующие ресурсы:

- данные: A1 TraceStore, A2 snapshot/history, состояния и branch-артефакты;
- интерфейсы: execute_verified, callback verifier, файловые транзакции/CLI;
- информация: текущие контракты, evidence refs, policy/source hashes;
- функции: planner, MergeProtocol, Git baseline/conflict/report adapters;
- время: ограниченные попытки, дедлайны, точки restart/reconciliation;
- пространства: изолированные worktree/temp state, копии состояния, защищённые backups.

Новые имена ниже — **предложение**, не существующие принятые реализации. Перед кодированием уточняются на минимальном diff. Acceptance не импортирует finalization; adapters зависят от них, не наоборот.

| M5. Адаптеры входов | Controller/daemon/bootstrap/cycle/nightly/API → один request/decision/finalizer | Таблица parity всех входов, не-0 exit при BLOCK/FAIL, никаких обходов через success=True; A2 capture не заменяется свежим |

M1 и M2 могут разрабатываться независимо после фиксации интерфейсов; M3/M4 проектируются совместно, сдаются ограниченными дельтами; M5 — после принятых контрактов M1/M3/M4. Нельзя частично включить M5 с прежним безусловным sink. Выпуск пакета — согласованный, не по отдельному зелёному файлу.

**Обязательное узкое расширение scope:** marker эффекта вместе с HP бессмысленен, если другой writer перепишет meta-state из старого кэша. Поэтому перед M4 составляется карта всех писателей этого файла; они используют общий A1 read/validate/modify/replace либо безопасно исключены из выпуска. Невозможность ограничить эту дельту — STOP/пересогласование, не скрытая переделка всего MetaCore. Общая health/death policy вне A3.

M1 не ходит к провайдеру и не выполняет ветки; M2 не заменяет Git rollback; M3 не строит новую очередь заданий; M4 не вводит новую БД/lock framework. A1 primitive и формат ack A2 сохраняются. Изменения их API — отдельный контракт и регрессионная приёмка.

## 5. Условие успеха и граница внешних эффектов

Request связывает schema/policy version, operation_id, contract_id, orchestrator, mode, **все обязательные ветки**, target/base/candidate revision и snapshot/storage identity там, где есть корзина. Evidence связывает эти поля с исходными находками, повторной проверкой дефекта, регрессиями/инвариантами и идентичностью независимого verifier; ссылки читаемы, digest совпадает. Один digest не доказывает смысловую правильность.

Сохраняется execute_verified: callable executor, отдельный callable verifier, валидные ветки, merged is True, непустое evidence и verifier is True. Разные функции сами по себе не доказывают независимость — проверяющий читает артефакты, не пересказывает merged-флаг исполнителя.

**Две точки контроля:** принять кандидат до внешней публикации там, где адаптер это позволяет; затем независимо подтвердить реально опубликованную revision до HP/ack. Если исполнитель уже сделал внешний merge, поздний veto не отменяет совершившееся: исход отмечается как merged-but-not-accepted/needs-reconciliation, без награды и без фиктивного rollback. Адаптер без безопасной границы prepare/publish/reconcile не допускается к production merge. Для него допустима только подготовка кандидата либо BLOCKED.

Simulation/review-only — диагностический режим, не accepted production result. --no-git сейчас не означает отсутствие всех Git-операций: он ограничивает M5 session commits, а не весь M6. План тестов не использует этот флаг как sandbox.

Для потока без корзины отсутствие ack допустимо только как явное NOT_APPLICABLE по контракту, а не из-за потерянного пути/capture. Новые награды/skill promotion не вводятся: A3 защищает существующее восстановление и не допускает бонусов из неподтверждённого сна; полный reward/learning lifecycle остаётся A6.

## 6. Частичные коммиты и повторы

operation_id и неизменяемый digest request фиксируются **до** dispatch; процессный in-memory set не является dedupe. Минимальные различимые факты: prepared → execution_started → external_result_observed → evidence_accepted → benefit_applied → basket_acknowledged либо NOT_APPLICABLE → complete. Точные transition/schema валидируются кодом будущего M3, не выбираются LLM в ответе.

- Marker операции и HP-изменение сохраняются в **одной** транзакции meta-state; отдельная receipt-запись не даёт exactly-once HP.
- Ack использует исходный A2 capture; поздние находки остаются. После ack retry не воскрешает событие.
- При HP-success/ack-failure восстанавливается только недостающий шаг: не повторять merge/HP и не писать rollback=True.
- При ack-success/receipt-failure восстановление опирается на сохранённое acknowledgement evidence; незавершённая квитанция не означает отсутствия ack.
- После внешнего merge без надёжной receipt нельзя вслепую повторять executor. Подтвердить target revision через согласованный адаптер либо MANUAL_RECONCILIATION.
- A1 сохраняет трассы, но сам по себе не гарантирует семантическую дедупликацию append; это отдельный контракт корреляции события в M3.
- Никакой JSON lock не удерживается через LLM/Git/долгое внешнее выполнение. Способ claim/finalizer сериализации ограничен существующими FileLease/store identity и дедлайнами.

Гарантия A3 — восстанавливаемые фазы и доказанная идемпотентность локальных эффектов, **не глобальная атомарность Git+HP+trace+basket и не универсальное exactly-once**.

Сначала RED подтверждённых дефектов на синтетическом состоянии, затем GREEN. Unit/contract — явные временные пути и внедрённые адаптеры; отдельная разрешённая Git-проверка только в одноразовом репозитории, не в рабочем/каноническом target. Бюджет проверок фиксируется до реализации: один владелец каждого утверждения, результаты не суммируются как независимые при повторе тех же методов. Обязательные регрессии/negative controls не заменяются лимитом инструментов. Нехватка бюджета → PARTIAL/BLOCKED и сохранённый пакет, не дополнительный непосчитанный круг. Денежный/токенный расход учитывать реальным источником; tool count не эквивалент стоимости.

## 8. Сшивка с OpenCode и разрешение диспатча

A3 — внутренний Python-контур. CLI-инструкции агента и вызовы nightly не доказывают, что native hook OpenCode реально вызывает этот код. В inspected scope такой hook не установлен. Реальная host-передача проверяется отдельно по TD-185, с actual session/agent/parentID/versions и artifact correlation.

TD-184 блокирует сертификацию nested specialized dispatch. Для **реализации A3** сначала либо устранить TD-184, либо получить явное отдельное разрешение на специализированные standalone CLI-сессии с host identity check. Исключение A2 не наследуется. General здесь разрешён только как честно названный read-only аналитик/плановый reviewer/deployer, не замена coder/reviewer/tester/auditor.

Цикл будущей реализации: worker → reviewer/tester → metadata-only auditor A → analyst → LIGHT → контролируемый release. Reviewer и auditor не работают одновременно; re-review только дельтой. Отчёты — файлы, схемы и factory_ctl решают gates/attempts/tribunal. Новый factory cycle, не переоткрытие DONE A1/A2. Бюджет/лимиты утверждаются до dispatch.

TD-185 не блокирует разработку плана и sandbox-кода A3, но до допуска A3 к рабочему ack/health и до заявления о сквозной интеграции выполняются оба уровня реальной передачи на явно заявленном маршруте. Невыполненный nested-сценарий остаётся BLOCKED, а standalone результат не называется nested-PASS.

Нет новых SDK/провайдеров, Polza/OAuth extraction, глобальных конфигурационных изменений или автоматической памяти. Непринятый guard и V2 semantic transport не считаются исправленными общим sleep-гейтом.

## 9. Внедрение и откат

1. Принять модульные контракты, scope M4, evidence schema и verifier adapters; разрешить фактический диспатч. Заморозить исходные hashes: a3_execution_map.json — база сравнения, не разрешение перезаписать будущий дрейф.
2. Выполнить M1–M5 и локальную приёмку, закрыть независимые замечания; код не активировать. Зафиксировать code/evidence manifest, change list и безопасность старых callers.
3. Для рабочего допуска пройти TD-185 и связанные host/guard/permission gates. Если они не пройдены, возможен только отдельно согласованный неактивный code-only пакет, с доказанно заблокированными зависимыми production-входами.
4. Инвентаризовать писателей не только DamageBasket, но и meta-state/operation receipts; получить новое операторское окно без повторных запусков. Старое подтверждение окна A2 не действует для A3.
5. Защитить полные backups кода/состояния/operation evidence, проверить canonical drift и согласованность всех адаптеров. Стейджинг, изолированные tests, пакетная по смыслу установка при остановленных писателях, raw hash check. Не объявлять несколько замен файлов атомарным каталоговым commit.
6. Production executor/verifier/daemon/nightly по умолчанию не включаются. Активация — отдельный контракт с целями, правами, независимым verifier, timeout/cancel, bounded canary и условиями остановки. Первый canary не восстанавливает health «за сам факт запуска».
7. При ошибке до новых рабочих эффектов — согласованный code rollback. После внешнего merge/HP/ack — сохранить новые данные/receipts и выполнить reconciliation; не откатывать историю/HP из старого backup и не затирать поздние находки. Неизвестный исход → BLOCKED, не фиктивное восстановление.

Sunset тестовых каталогов — finally cleanup; отклонённые кандидаты/ветки/отчёты сохраняются по действующему контракту, не удаляются как будто успешные. Новые временные совместимые обходы имеют явный owner/acceptance/sunset, не превращаются в постоянную вторую архитектуру.

## 10. Решения перед реализацией

- Фактический маршрут специализированных агентов A3 и отдельное разрешение при открытом TD-184.
- Конкретный независимый verifier и authoritative target/finding/revision evidence для каждого адаптера; отсутствие → BLOCKED, не permissive default.
- Минимальный scope общей транзакции всех meta-state writers и схема stable operation/effect markers.
- Политика report/restore/trace-failure, режим NOT_APPLICABLE для потоков без корзины и ручная reconciliation внешнего неопределённого исхода.
- Согласованный бюджет, команды валидаторов и stop criteria; критерии завершения TD-185 на разрешённом маршруте.

**Итог:** план готовит изменения существующего контура W7/W13 и его границ W5/W6, а не включает автономное самоисправление. A1/A2 code-only принятие сохраняется. Пока нет реализации/тестов A3, утверждения этого документа — требования, не PASS.
