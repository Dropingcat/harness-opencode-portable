# Блокнот канонов и критериев агентной системы

> Источник-канон: https://neuraldeep.ru/learn/books/agenty-vajbkoding (45 глав + приложения)
> Назначение: критерии для разработки, ревью и отказоустойчивости цикла сна / демона аудитора / всей harness-обвязки.
> Формат: глава → канон → проверка в нашем коде → что исправить.

---

## Глава 1. Что такое агент

**Каноны:**
1. Агент = модель + инструкции + инструменты + контекст в цикле.
2. **Спектр агентности**: одиночный вызов → процесс → агент с выбором → многоагентная система. Свобода, непредсказуемость и цена ошибки растут вправо.
3. **Рабочий порог**: «агент — посредник, который сам собирает контекст и сам выбирает инструменты».
4. **Качество агента = качество его инструментов и их описаний.** Не размер модели.
5. 5 вопросов разбора: есть ли цикл? инструменты фиксированы или выбор? кто собирает контекст? что при ошибке? сколько свободы?

**Проверка в нашем коде:**
- [x] Цикл есть (meta_daemon, factory_ctl state machine).
- [ ] Инструменты описаны качественно? (task_skill_templates — проверено, шаблоны есть, но не все с guard).
- [x] Контекст собирает обвязка (project_context.py, resolve_bundle).
- [ ] Что при ошибке? (в agent_supervisor есть restart; в meta_daemon — retry нет, только damage).

**Что исправить:** добавить явные описания инструментов с `forbidden` (канон: описание = часть работы); в цикле сна при ошибке ветки — не «молча идти дальше», а retry/откат/остановка.

## Глава 2. Анатомия агента

**Каноны:**
1. 6 слоёв: модель, цикл, инструменты, контекст, память, **проверка (снаружи, строишь сам)**.
2. Модели отдавай догадку, всё надёжное — коду.
3. Формат, описанный словами, нарушается в ~1 случае из 10 → контракт обеспечивает код, не абзац.
4. Минимум цикла: (а) явный признак завершения, (б) лимит ходов, (в) правило при ошибке инструмента, (г) **запрет объявлять готовым непроверенное**.
5. Инструмент = контракт: схема входа, предусловия, побочные эффекты, таймаут, **идемпотентность**, права.
6. Контекст платный и ограничен; внимание неравномерно (начало/конец лучше середины).
7. Память ≠ контекст.

**Проверка:**
- [x] Явный признак завершения (factory_ctl done_condition, agent_loop done-file/regex/tool).
- [x] Лимит ходов (max_iters, attempt_limit).
- [ ] Идемпотентность инструментов НЕ описана (downloader, book_finder, dom_builder) → риск двойного вызова.
- [x] Запрет «готово без проверки» — factory gate (reviewer+tester+auditor).
- [ ] Формат ответа субагентов обеспечивается кодом? (contract_validator — да, есть).

**Что исправить:** документировать идемпотентность каждого tools/*.py (поле в шаблоне); в agent_supervisor при сбое инструмента — retry с ограничением (сейчас только отклонения).

## Глава 6-7. Спецификация вместо задания / Требования, понятные агенту

**Каноны (пересказ):**
1. Спецификация ≠ задание: задание говорит «что сделать», спецификация — «что считается готовым» (проверяемые критерии).
2. Требование понятно агенту, если: однозначно, проверяемо, не противоречит другим, имеет область применения.
3. Критерии готовности на каждом пункте — главный антидрейфовый механизм.

**Проверка:**
- [x] factory_ctl: контракт с acceptance (contract_validator).

- [ ] Контракты субагентов (claim-parser/fact-checker) — есть acceptance, но не всегда «проверяемое состояние».

## Глава 12. Скиллы: механика и жизненный цикл

**Каноны:**
1. В контексте висят ТОЛЬКО описания; тело грузит модель по решению.
2. **Описание важнее тела**: перечисли ситуации применения + явно отсеки неподходящие.
3. Скилл = подписка, не разовая покупка. Окупаемость = повторы × стоимость ручного прохода.
4. Клади стабильное; живой текст — не в скилл.
5. Срок годности — недели; ревьюй как код; удаляй без соплей.
6. Признаки удалить: не помнишь что делает, месяц не грузился, дублирует модель, лезет не туда (описание широкое), интерфейс поменялся.
7. **Ниша скилла**: знания, которых нет ни в коде, ни в обучающих данных (внутренние соглашения, вендор).
8. Скилл против склонности модели (яркая инструкция) — усиливает перекос. Работает детерминированная проверка да/нет.

**Проверка:**
- [x] Шаблоны в tool_skill_templates (arxiv_search и др.) — есть описание + forbidden.
- [x] Новый task-context-assessment — описание с триггерами и запретами (после фикса M4).
- [ ] Нет «мета-скилла» (как делать/проверять другие скиллы) — это наш skill_master (есть в meta, не в portable ещё?).
- [ ] Нет предполётной проверки версии скилла.
- [ ] ~40 скиллов в ~/.config/opencode/skills — налог на каждый ход; нет ревью/чистки.

**Что исправить:** skill_master перенести в portable (M10); добавить «предполётную проверку версии» в шаблон скилла; провести ревью скиллов (удалить мёртвые).

## Глава 13. Хуки и детерминированные гарантии

**Каноны:**
1. Хук = код, который система запускает сама по событию. Отрабатывает ВСЕГДА, контекст не жрёт.
2. Хук нужен там, где есть процесс (назови событие). Иначе — ритуал.
3. Ошибку возвращай в сессию С ОБЪЯСНЕНИЕМ, не молча (молча → обход).
4. Хук после сжатия: перечитать ключевое (работает 8/10, инструкция — никогда).
5. Разделяющий критерий: обратимость шага. Откатывается за минуту — без хука. Необратимо — хук.
6. После установки хука — вычисти строку из правил (две реализации разъедутся).
7. Память >15-20k символов сыпется.

**Проверка:**
- [x] hooks/coder-dom-verify.sh (перед коммитом кода).
- [ ] НЕТ хука «git-session-sync» (авто-цепляние изменений сессии) — ЭТО M5 из нашего плана!
- [ ] НЕТ хука «восстановление после сжатия» (agent должен перечитывать ключевое).
- [ ] НЕТ хука «завершение задачи → отчёт/уведомление» (есть kanban_report, но не хук).
- [ ] НЕТ хука «коммит → проверка опасных паттернов» (TD-163 react_auditor — есть в meta, не в portable).

**Что исправить:** M5 (git_session_sync как хук), хук восстановления после сжатия (в agent_supervisor/agent_loop), хук завершения задачи.

## Глава 15. Контекст как единственный ресурс

**Каноны:**
1. Контекст оплачивается ЦЕЛИКОМ каждый ход → длинный разговор дорожает нелинейно.
2. Внимание неравномерно: начало/конец лучше середины.
3. Контекстный движок решает, ЧТО положить; память/поиск — источники.
4. Стабильное — в начало, изменчивое — в конец (иначе кеш ломается, каждый ход по полной).
5. Непротиворечивое — дать с запасом; противоречивое — УБИРАТЬ (а не сокращать).
6. Самая дорогая ошибка — гонять сильную модель по файлам вместо работы.
7. Стадии: всё в один запрос → разделение по ролям → управление объёмом → управление вниманием.

**Проверка:**
- [ ] Нет явного контекст-движка (что куда класть) — project_context.py частично.
- [ ] Нет управления кешем (стабильное в начало).
- [ ] Субагенты получают минимальный набор (ch20) — частично (капсулы).
- [ ] Сжатие контекста — compaction auto в opencode.jsonc, но нет хука восстановления.

**Что исправить:** контекст-движок (порядок сборки: системное → правила → цель → история → изменчивое); документировать кеш-правило; субагентам — только нужные инструменты.

## Глава 17. Память: файлы, векторы, нити

**Каноны:**
1. 3 вида: файлы (хранилище, слабый поиск), векторы (поиск по смыслу), нити (история решений с обоснованиями).
2. Подмешивай найденное ДО вызова модели, не давай инструмент поиска.
3. Память без времени врёт (противоречащие факты) → храни дату, вес по времени.
4. Порог близости неверен → переранжирование или доп. отсев.
5. **Уборка в фоне обязательна** (ночная свёртка). Без неё деградирует любая память.
6. Объём памяти >15-20k символов сыпется.
7. Нити хранят «почему», не факты.

**Проверка:**
- [x] memory_l1/l2/l3_policy + memory_registry (L3 lessons) + memory_circulator (L2→L3).
- [x] memory_router (M2) — namespaces + session tracker.
- [ ] Нет ночной свёртки (свёртка дневных→недельных→месячных).
- [ ] Векторный поиск по памяти — есть chroma_indexer, но не «подмешивание до вызова».
- [ ] Нити (история решений) — нет; есть trace_store (частично).

**Что исправить:** ночная свёртка памяти (M-долг); подмешивание L3-уроков до вызова (memory_injector — есть в meta, перенести); нити решений (напр. для цикла сна: почему выбрана ветка).

## Глава 19. Субагент: когда помогает, когда мешает

**Каноны:**
1. Делегируй ради ИЗОЛЯЦИИ КОНТЕКСТА и ПАРАЛЛЕЛЬНОСТИ, не ради экономии.
2. Издержки координации есть всегда (передача, потеря контекста, сборка, противоречия).
3. Тесно связанные решения — у одного ответственного. **Писать код субагентами запрещено** (2 куска в 2 головах расходятся по интерфейсу).
4. Правило для роя: «копай и возвращайся, решать будем вместе». Не делегируй принятие решений.
5. Защита от взрыва: глубина (проверь экспериментом!), лимит одновременных, потолок расхода, дешёвая модель для первого запуска, проверь наследование level усилий.
6. Одноразовые исполнители предпочтительнее постоянных ролей (меньше состояния).

**Проверка:**
- [x] task-субагенты в opencode (subagent_depth: 2 — надо проверить, что реально ограничивает).
- [x] Контракты субагентов (worker/reviewer/tester/auditor).
- [ ] Нет потолка расхода на задачу в субагентском цикле (TD-120: run_research budget).
- [ ] Связанный код пишут воркеры ПО ОТДЕЛЬНОСТИ (наш фабричный подход) — риск расхождения интерфейсов. Смягчение: контракт + интеграция оркестратором.
- [x] Изоляция контекста субагентов (чистая сессия) — да.

**Что исправить:** явный потолок расхода на субагента; проверка глубины экспериментом; дешёвая модель для разведки.

## Глава 20. Многоагентность и рои

**Каноны:**
1. Рои хороши на СБОРЕ и СТРУКТУРИРОВАНИИ, слабы на ВЫБОРЕ.
2. Топологии: цепочка (медленно, ошибки копятся), веер (параллельно, сборка дорога), дерево (масштаб, взрыв).
3. Веер: разбить → раздать → собрать → **СВЕСТИ в одну голову** (критично, часто пропускают).
4. Ошибки копятся НЕЛИНЕЙНО: долго стабильно → резкий срыв. Схема отработала 5 раз ≠ отработает 6-й.
5. Ограничивай: глубина 1 уровень, десятки агентов, потолок расхода.
6. Оркестратор держит чистый контекст, обвязка собирается субагентам под задачу (мин. набор инструментов).
7. Ферма умножает то, что есть.

**Проверка:**
- [x] Цикл сна = веер: damage → кластеры → ветки fix/* → merge (сведение в одну голову = merge_protocol).
- [x] Оркестратор чистый контекст (meta_daemon почти ничего не знает).
- [ ] Нет Monte-Carlo прогонов (M8) — чтобы измерить разброс (нелинейность ошибок!).
- [ ] Потолок расхода на сон не задан.
- [ ] Сведение результатов сна — merge_protocol есть, но не «чистый replay» (TD-166).

**Что исправить:** M8 (Monte-Carlo, вариация hp/threshold) — измерение разброса; потолок расхода на сон; clean replay после merge.

## Глава 22. Ревью

**Каноны:**
1. Нельзя быть себе судьёй: предвзятость создаётся КОНТЕКСТОМ, не моделью. Чистая сессия решает.
2. Ревью = узкая работа → хорошо делегируется (в отличие от разработки).
3. Смотри в 3 точках: на входе (как понял постановку), в процессе (чем занят), на выходе (совпадает ли с замыслом).
4. Вместо чтения кода — пересказ обычными словами + «что решил сам, чего не просили».
5. «Оцени качество» не работает. Работает список вопросов с ответом да/нет.
6. Цикл: полировка (3-5 проходов) → **схлопывание** (убрать наросшее).
7. Кто ревьюит: та же модель чистая сессия / другая модель (уникальные находки) / человек.

**Проверка:**
- [x] factory: code-reviewer (чистая сессия, scope_in/out, falsification).
- [x] Трибунал при конфликте (code-auditor).
- [ ] Нет этапа «схлопывание» в фабрике (полировка есть, схлопывания нет).
- [ ] Нет ревью «на входе» (как воркер понял постановку) — только контракт-валидация.
- [ ] Нет пересказа обычными словами (вопрос «что решил сам»).

**Что исправить:** этап схлопывания после полировки; ревью «на входе» (первый ответ воркера); вопрос «что решил сам» в ревью.

## Глава 23. Эвалы

**Каноны:**
1. Один прогон = точка из распределения. Считай ДОЛЮ успешных из N попыток.
2. Шкалы 1-5 выкинь. Бинарно: прошло/не прошло + критика текстом.
3. Судью строй из объяснений эксперта (~30 размеченных примеров), не из абстрактных критериев.
4. Считай по СРЕЗАМ (функция/сценарий/роль), не общим средним.
5. Смещения судьи: позиционное (первый выигрывает) → перемешивай; многословное (длинный кажется лучше).
6. **Суди траекторию, не ответ** (какие инструменты, порядок, сколько оступился).
7. Скилл проверяй против базовой линии БЕЗ него.
8. Постоянно живут только проверки. Сначала измерение, потом обвязка.

**Проверка:**
- [ ] Нет эвал-набора (10 типовых задач × 3 прогона).
- [ ] M8 (Monte-Carlo) — это и есть эвал цикла сна (частота успеха, разброс).
- [x] Аудитор (external) — бинарно + критика (да).
- [ ] Нет суда по траектории (session_analyzer tools — частично).

**Что исправить:** базовый эвал-набор (10 задач из реальной работы); M8 прогоны; суд по траектории в аудиторе.

## Глава 24. Детерминированные проверки вместо уговоров

**Каноны:**
1. Управление через правила НЕНАДЁЖНО: агент выполняет букву, нарушает смысл.
2. Запрет без правильного пути → изворотливость.
3. Проверку пишет НЕ тот, кого проверяют (человек/отдельный агент/код).
4. Слово «всегда/никогда/обязательно» в инструкции = признак, что нужно кодом.
5. Формат словами нарушается 1/10 → контракт кодом.
6. Архитектурные требования — линтером.
7. Плохая обвязка обнуляет сильную модель (13% → 38% от настроек окружения!).
8. Пересказ потока обычными словами закрывает «расхождение реализации с замыслом».

- [x] contract_validator (JSON-контракты кодом).
- [x] Аудитор не читает код (процессный).
- [ ] Слова «всегда» в правилах/промптах не вычищены (нужен grep и перевод в хуки/проверки).
- [ ] Нет линтера на слоистость/импорты (архитектурные ограждения).
- [ ] «Проверка результата без чтения кода» (пересказ) — не в фабрике.

## Глава 26. Ночной прогон

**Каноны:**
1. Ночной прогон = результат дня ПОДГОТОВКИ, не команда.
2. В запросе обязательно: «человека нет», «пиши прогресс в план», «блокировку помечай и пропускай», «иди по порядку», «перечитывай спецификацию перед каждым пунктом».
3. Схема по одному пункту < весь план (меньше сюрпризов, лечит переусложнение).
4. Чекпоинты в спецификации (проверяемое состояние) — утром читаешь их, не код.
5. Файл прогресса на диске — страховка от сжатия/обрыва/лимита.
6. Когда НЕ стоит: архитектура не устоялась, нет проверок, полные права.

**Проверка:**
- [ ] Файл прогресса в автономном цикле — есть (sleep_contract, meta_state), но не «план с прогрессом».
- [ ] Чекпоинты в спецификациях субагентов — нет.
- [ ] Пункт «перечитывай спецификацию перед каждым пунктом» — нет (в agent_loop continue_prompt есть, но не спецификацию).

**Что исправить:** шаблон автономного прогона (прогресс в план, чекпоинты, перечитывание).

## Глава 27. Дрейф намерения

**Каноны:**
1. Намерение распадается НЕЛИНЕЙНО; лишние ограничения ускоряют распад.
2. Лучше 3 условия с проверкой, чем 15 без проверки.
3. Агент предпочитает рискованное действие уточняющему вопросу → делай вопрос ОБЯЗАТЕЛЬНЫМ проверкой.
4. **Строка-лекарство**: «Работаем по документации и фактам, а не по памяти. Перед любым выводом опираемся и ссылаемся на источник».
5. Признаки дрейфа: «вероятно/скорее всего», пересказ короче, решает соседнюю задачу, ссылается на своё решение, отчёты общие.

## Глава 34-35. Разрушительные действия и изоляция

**Каноны:**

11. Механизм выключения пиши одновременно с включением.

## Приложение Б. Чек-листы (прямые критерии)

1. **Перед длинной сессией**: спецификация+критерии; файл прогресса; порог сжатия; хук восстановления (проверен!); стабильное в начало; потолок расхода; строка про документацию.

3. **При скилле**: повторяется?; модель без него?; описание с ситуациями; явные «не нужен»; стабильное внутри; базовая линия; проверка версии; владелец.
4. **При правиле**: не выяснит сам?; эксперимент с/без; причина; область; нет противоречий; не место в описании/скилле/памяти/хуке; файл в разумном объёме.
5. **После инцидента**: восстановление первым; журналы не объяснения; почему смог; права не правила; проверка на класс; восстановление проверено; запись туда где прочитают.
6. **При выборе модели**: знание о задаче (как/что/в чём); цена ошибки; уровень усилий под размер; наследование субагентами; дешёвая модель для навигации; повторяемость замерена.
7. **Независимость от поставщика**: сколько мест на имя модели; что умрёт при недоступности; вторая связка; скиллы под задачу не модель; эвалы на второй модели; формат переживает смену инструмента; отпечаток машины.
