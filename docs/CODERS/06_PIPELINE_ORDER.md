# 06_PIPELINE_ORDER.md — Порядок пайплайна фабрики (для оркестратора)

**Дата:** 2026-10-05 · **Статус:** АКТИВЕН · **Версия:** 1.0
**CWD:** `E:\opencode_harness_portable`

> Назначение: контракт для ОРКЕСТРАТОРА — как запускать звенья фабрики правильно. Файл самодостаточен: определяет обязательную последовательность, минимальный контекст каждого звена, правила исключений. Ревьюер/аудитор вставляют этот файл в свой промпт ЧАСТИЧНО — оркестратор решает, какие разделы дать каждому звену (по §3 и §5).

---

## 1. ЦЕЛЬ

Единый порядок запуска звеньев фабрики, который гарантирует: **каждое звено получает полный контекст** (спецификации, артефакты, вердикты предыдущих звеньев) и **не додумывает** входные данные.

Контракт появился из опыта B1-T2 / M0-a / B3-T1:

1. **Ревьюер и аудитор не получали спецификаций в контекст** → не могли проверить соответствие, ждали или додумывали. Решение: прикладывать тексты спецификаций прямо в промпт + давать фокус на конкретной задаче.
2. **Аудитор ждал вердикт ревьюера** (звенья запускались параллельно) → не мог сослаться. Решение: последовательность `worker → reviewer → auditor → deployer`, аудитор получает вердикт ревьюера и его артефакты.
3. Техдолги фиксируются по контракту 05 (уже есть, не дублируется здесь).

---

## 2. ПОСЛЕДОВАТЕЛЬНОСТЬ (обязательная)

```
worker → reviewer → auditor → deployer
```

- Строго последовательно, без параллельного запуска ревьюера и аудитора.
- Каждый следующий шаг начинается только после получения результата предыдущего.
- Деплоер — только при `APPROVE` обоих звеньев (иначе возврат на ревью/воркера, §4).

**Альтернатива (допустимая):** если звенья всё же запускаются параллельно, оркестратор обязан дать каждому из них доступ к сессии и артефактам другого (общий файл-артефакт на диске + явные пути в промпте). Но это НЕ штатный режим.

---

## 3. КОНТЕКСТ ДЛЯ КАЖДОГО ЗВЕНА (что прикладывать в промпт)

Общий принцип: **файлы спецификаций прикладываются В КОНТЕКСТ (цитатами/текстом секций), а не ссылками** — у субагентов нет доступа к диску в полном объёме. Необязательный контекст даётся только если не размывает фокус.

### 3.1 Воркер (coder-worker)

| Поле | Что дать |
|------|----------|
| **Спецификация блока** | текст секции `B*-T*` из `01_BLOCKS_B1_B5.md` ИЛИ секции `W*` из `02_BRANCHES_W1_W13.md` (прикладывать цитатой) |
| **Текущее состояние файлов** | результат `read` затрагиваемых файлов (что есть сейчас, на чём строится) |
| **DoD** | определение done из спецификации блока, дословно |
| **Правила** | НЕ коммитить, НЕ выходить за scope блока, CWD=portable, Python `.venv\Scripts\python.exe` |
| **Выход** | файл-артефакт (`worker_<ID>.json` или изменённый файл) + отчёт со заявленными DoD |

### 3.2 Ревьюер (code-reviewer)

| Поле | Что дать |
|------|----------|
| **Спецификация блока** | **ПОЛНЫЙ ТЕКСТ секции — прикладывать, не ссылкой!** |
| **Артефакт воркера** | `worker_<ID>.json` или изменённый файл |
| **Отчёт воркера** | его заявленные DoD (что воркер утверждает как сделанное) |
| **Контракт 05** | вставить `05_REVIEWER_AUDITOR_TECHDEBT.md` — фиксировать найденные техдолги в `docs/PROBLEMS_REGISTER.md` |
| **Фокус** | соответствие спеке, DoD, ЛОЖНЫЕ ОТЧЁТЫ (заявлен PASS при фактическом FAIL), качество кода |
| **Выход** | вердикт `APPROVE` / `REQUEST_CHANGES` / `REJECT` + TD-* (если найдены) + `reviewer_<ID>.json` |

### 3.3 Аудитор (code-auditor)

| Поле | Что дать |
|------|----------|
| **ВЕРДИКТ РЕВЬЮЕРА** | **обязательно — прикладывать текст вердикта!** |
| **Артефакты** | `worker_<ID>.json` + `reviewer_<ID>.json` |
| **Спецификация блока + смежные** | текст секции блока + зависимости (что идёт дальше, что блокирует) — из `00_INDEX.md` §4 (критический путь), `01`, `02` |
| **Контекст** | EXP-готовность, интеграция с соседними `B*`/`W*` |
| **Контракт 05** | вставить `05_REVIEWER_AUDITOR_TECHDEBT.md` |
| **Фокус** | процесс + интеграция (не пере-ревьюить код — это сделал ревьюер) |
| **Выход** | вердикт `APPROVE` / `REQUEST_CHANGES` / `REJECT` + TD-* (если найдены) + `auditor_<ID>.json` |

### 3.4 Деплоер (general по контракту 04)

| Поле | Что дать |
|------|----------|
| **Вердикты ОБОИХ** | ревьюер + аудитор; деплой ТОЛЬКО если оба `APPROVE` |
| **Список артефактов для коммита** | пути относительно корня portable (код/конфиг/скрипты, `reviewer_<ID>.json`, `auditor_<ID>.json`, `docs/PROBLEMS_REGISTER.md`, `.gitignore`) |
| **Контракт 04** | вставить `04_DEPLOYER_CONTRACT.md` полностью (включая шаг 3.5: `PROBLEMS_REGISTER.md` при наличии TD-*) |
| **Выход** | `DEPLOYED` / `BLOCKED` / `SKIPPED_NO_APPROVE` (по §4 контракта 04) |

## 4. ПРАВИЛА ПОСЛЕДОВАТЕЛЬНОСТИ

1. **НЕ запускать ревьюера и аудитора параллельно** — аудитор зависит от вердикта ревьюера. Только `worker → reviewer → auditor → deployer`.
2. Если ревьюер `REQUEST_CHANGES` — аудитор получает вердикт + причины. Аудитор может `APPROVE` (если `REQUEST_CHANGES` по коду не влияет на процесс/интеграцию) или вернуть воркеру.
3. Если ОБА `REQUEST_CHANGES` (или `REJECT`) — блок возвращается воркеру с **объединённым списком правок** (ревьюер + аудитор в одном списке, без дублей).
4. Если ревьюер `APPROVE` И аудитор `APPROVE` → деплоер.
5. Прикладывать файлы спецификаций **В КОНТЕКСТ** (цитировать секции), не только ссылаться — у субагентов нет доступа к диску в полном объёме.
6. Давать ФОКУС: «проверь ТОЛЬКО X, не уходи в Y» — субагенты склонны расширять scope. Формула: `Задача: <блок>. Фокус: <что проверять>. Вне фокуса: <что не трогать>.`
7. Каждый вердикт — файл-артефакт (`reviewer_<ID>.json`, `auditor_<ID>.json`): деплоер коммитит его как часть результата блока.
8. Техдолги фиксирует ТОТ, КТО НАШЁЛ (контракт 05), TD-ID перечисляются в вердикте.

## 5. МАТРИЦА КОНТЕКСТА (быстрая справка оркестратора)

| Звено | Обязательный контекст | Необязательный | Фокус |
|-------|----------------------|----------------|-------|
| worker | спека блока (цитатой), состояние файлов | полная картина (обзор трекера) | сделать по спеке, не выходить за scope |
| reviewer | спека блока (ПОЛНЫЙ текст), worker JSON, отчёт воркера | смежные блоки (если влияют) | соответствие спеке + ложные отчёты |
| auditor | вердикт reviewer (текстом), worker+reviewer JSON, спека блока, смежные | EXP-готовность, прогноз интеграции | процесс + интеграция с соседними B*/W* |
| deployer | вердикты обоих (текстом), список артефактов | детали блока (не нужны) | коммит+push+TD (контракт 04) |

## 6. ЧТО ДЕЛАТЬ ПРИ ИСКЛЮЧЕНИЯХ

| Ситуация | Действие |
|----------|----------|
| Ревьюер `REJECT` (не `REQUEST_CHANGES`) | Блок возвращается воркеру СРАЗУ, аудитор не запускается до исправления. Вердикт + причины — воркеру. |
| Ревьюер `REQUEST_CHANGES`, аудитор `APPROVE` | Деплой НЕ выполняется (нужен APPROVE обоих). Правки по списку ревьюера → воркер → повторное ревью (аудит повторно не нужен, если процесс/интеграция не затронуты). |
| Оба `REQUEST_CHANGES` | Воркер получает объединённый список правок (без дублей) → повторный цикл. |
| Оба `APPROVE` | Деплоер (контракт 04), статус `DEPLOYED`. |
| Аудитор не согласен с вердиктом ревьюера (`APPROVE` ревьюера, но аудитор `REJECT`) | Эскалация оркестратору: конфликт звеньев. НЕ деплоить. Оркестратор решает (может подключить третье мнение или трибунал). |
| Воркер заявил DoD PASS, а ревьюер нашёл FAIL | Техдолг по контракту 05 (ложный отчёт) + возврат воркеру. |
| Нет вердикта одного из звеньев | Стоп до деплоя. Оркестратор дозапускает звено (не заменяет его додумыванием). |
| Артефакт звена не существует (путь не найден) | Не выдумывать замену. Зафиксировать и спросить воркера/оркестратора. |
| Спека блока изменилась во время цикла | Остановить цикл, перечитать актуальную секцию, перезапустить с воркера (старый контекст аннулирован). |
| 401 при push / отказ git-хука | По контракту 04 §6: `BLOCKED_NEED_WRITE_TOKEN` / исправить по сообщению хука, НЕ обходить. |

## 7. СВЯЗЬ С ДРУГИМИ КОНТРАКТАМИ

| Контракт | Связь |
|----------|-------|
| **`00_INDEX.md`** | Карта пакета, критический путь (§4), порядок блоков/траншей. Определяет, какой блок запускать следующим. |
| **`01_BLOCKS_B1_B5.md`** | Спецификации B-блоков — источник контекста для воркера/ревьюера/аудитора. |
| **`02_BRANCHES_W1_W13.md`** | Спецификации W-веток — источник контекста для W-блоков. |
| **`03_ACCEPTANCE.md`** | DoD/приёмка (матрёшка M0–M6, EXP) — критерии готовности, на которые ссылаются вердикты. |
| **`04_DEPLOYER_CONTRACT.md`** | Контракт деплоера: вставляется в промпт деплоеру, шаг 3.5 — `PROBLEMS_REGISTER.md`. |
| **`05_REVIEWER_AUDITOR_TECHDEBT.md`** | Фиксация техдолгов TD-*: вставляется ревьюеру и аудитору, TD-ID — в вердиктах. |

**Порядок использования (памятка оркестратору):**

1. Взял блок из `00_INDEX.md` §4 (критический путь).
2. Достал секцию спеки из `01`/`02`.
3. Запустил воркера (контекст §3.1) → получил артефакт + отчёт.
4. Запустил ревьюера (контекст §3.2 + контракт 05) → вердикт + `reviewer_<ID>.json`.
5. Запустил аудитора (контекст §3.3 + контракт 05 + ВЕРДИКТ РЕВЬЮЕРА) → вердикт + `auditor_<ID>.json`.
6. При двух `APPROVE` → деплоер (контракт 04 + список артефактов).
7. При `REQUEST_CHANGES`/`REJECT` → §4/§6 (возврат воркеру или эскалация).
