Файл самодостаточен: определяет обязательную последовательность, минимальный контекст каждого звена, правила исключений. Ревьюер/аудитор/аналитик/ресерчер вставляют этот файл в свой промпт ЧАСТИЧНО — оркестратор решает, какие разделы дать каждому звену (по §3 и §5).

## 1. ЦЕЛЬ

Единый порядок запуска звеньев фабрики, который гарантирует: **каждое звено получает полный контекст** (спецификации, артефакты, вердикты предыдущих звеньев) и **не додумывает** входные данные.

Контракт появился из опыта B1-T2 / M0-a / B3-T1:

1. **Ревьюер и аудитор не получали спецификаций в контекст** → не могли проверить соответствие, ждали или додумывали. Решение: прикладывать тексты спецификаций прямо в промпт + давать фокус на конкретной задаче.
2. **Аудитор ждал вердикт ревьюера** (звенья запускались параллельно) → не мог сослаться. Решение: последовательность `worker → reviewer → auditor → … → deployer`, аудитор получает вердикт ревьюера и его артефакты.
3. Техдолги фиксируются по контракту 05 (уже есть, не дублируется здесь).
4. **Аналитик/ресерчер не были в цикле** → разрозненные находки ревью/аудита оставались несистематизированными, «материал для работы» (сводка проблем, приоритеты, факты о неперенесённом) не готовился, деплоеру и оркестратору не хватало целостной картины. Решение: после аудитора вставляются звенья `analyst → researcher`, готовящие материал перед деплоем (контракт 08).

---

## 2. ПОСЛЕДОВАТЕЛЬНОСТЬ (обязательная)

```
worker → reviewer → auditor → analyst → researcher → deployer
```

- Строго последовательно, без параллельного запуска ревьюера и аудитора, а также аналитика и ресерчера (ресерчер зависит от сводки аналитика).
- Каждый следующий шаг начинается только после получения результата предыдущего.
- Деплоер — только при `APPROVE` ревьюера И аудитора, и после отработки аналитика/ресерчера без критичных находок (иначе возврат на ревью/воркера, §4).

**Альтернатива (допустимая):** если звенья всё же запускаются параллельно, оркестратор обязан дать каждому из них доступ к сессии и артефактам другого (общий файл-артефакт на диске + явные пути в промпте). Но это НЕ штатный режим.

## 3. КОНТЕКСТ ДЛЯ КАЖДОГО ЗВЕНА (что прикладывать в промпт)

Общий принцип: **файлы спецификаций прикладываются В КОНТЕКСТ (цитатами/текстом секций), а не ссылками** — у субагентов нет доступа к диску в полном объёме. Необязательный контекст даётся только если не размывает фокус.

### 3.1 Воркер (coder-worker)

| Поле | Что дать |
|------|----------|
| **Спецификация блока** | текст секции `B*-T*` из `01_BLOCKS_B1_B5.md` ИЛИ секции `W*` из `02_BRANCHES_W1_W13.md` (прикладывать цитатой) |
| **Текущее состояние файлов** | результат `read` затрагиваемых файлов (что есть сейчас, на чём строится) |
| **DoD** | определение done из спецификации блока, дословно |
| **Правила** | НЕ коммитить, НЕ выходить за scope блока, CWD=portable, Python `.venv\Scripts\python.exe` |
| **Выход** | файл-артефакт (`worker_<ID>.json` или изменённый файл) + отчёт со заявленными DoD |

### 3.2 Ревьюер (code-reviewer)

| Поле | Что дать |
|------|----------|
| **Спецификация блока** | **ПОЛНЫЙ ТЕКСТ секции — прикладывать, не ссылкой!** |
| **МАТЕРИАЛ ДЛЯ РАБОТЫ** | спека блока (цитатой) + `worker_<ID>.json` + отчёт воркера (заявленные DoD) + `docs/PROBLEMS_REGISTER.md` (актуальные TD-*) + прошлые вердикты по блоку (если был `REQUEST_CHANGES` ранее — что уже просили исправить). **Если материала нет — фиксировать «материал не найден, проверять с нуля», НЕ выдумывать** |
| **Артефакт воркера** | `worker_<ID>.json` или изменённый файл |
| **Отчёт воркера** | его заявленные DoD (что воркер утверждает как сделанное) |
| **Контракт 05** | вставить `05_REVIEWER_AUDITOR_TECHDEBT.md` — фиксировать найденные техдолги в `docs/PROBLEMS_REGISTER.md` |
| **Скилы** | `adversarial-critic-checklist` — **обязательный**: структурированная критика (6 проверок: domain coverage, fact-concept consistency, concept diversity, source specificity, TRIZ correctness, estimates realism; severity critical/major/minor; пост-валидация); `review` — независимое ревью с evidence-backed findings; `doubt-driven-development` — при сомнениях в нетривиальных решениях |
| **Тулзы** | `read`, `grep`, `glob` (проверка кода/артефактов), `git status` / `git diff` (что реально изменено) — через доступные инструменты; не верить отчёту воркера на слово |
| **Фокус** | соответствие спеке, DoD, ЛОЖНЫЕ ОТЧЁТЫ (заявлен PASS при фактическом FAIL), качество кода |
| **Выход** | вердикт `APPROVE` / `REQUEST_CHANGES` / `REJECT` + TD-* (если найдены) + `reviewer_<ID>.json` |

### 3.3 Аудитор (code-auditor)

| Поле | Что дать |
|------|----------|
| **ВЕРДИКТ РЕВЬЮЕРА** | **обязательно — прикладывать текст вердикта!** |
| **МАТЕРИАЛ ДЛЯ РАБОТЫ** | всё, что у ревьюера (спека блока цитатой, `worker_<ID>.json`, отчёт воркера, `docs/PROBLEMS_REGISTER.md`) + вердикт ревьюера + смежные блоки (зависимости: что идёт дальше, что блокирует — из `00_INDEX.md` §4, `01`, `02`) + EXP-статус (какие EXP-протоколы подтверждены/нужны). **Если материала нет — «материал не найден, проверять с нуля» (не выдумывать)** |
| **Артефакты** | `worker_<ID>.json` + `reviewer_<ID>.json` |
| **Спецификация блока + смежные** | текст секции блока + зависимости (что идёт дальше, что блокирует) — из `00_INDEX.md` §4 (критический путь), `01`, `02` |
| **Контекст** | EXP-готовность, интеграция с соседними `B*`/`W*` |
| **Контракт 05** | вставить `05_REVIEWER_AUDITOR_TECHDEBT.md` |
| **Контракт 07** | вставить `07_AUDITOR_DILIGENCE.md` — въедливость, триггеры копания, секция 0 в отчёте |
| **Скилы** | `ariz-contradiction-resolution` — при противоречиях вердиктов (8-шаговое разрешение: input/operation/output/validation_rule на шаг); `verify` — реальные проверки с результатом pass/fail/not-tested; `doubt-driven-development` — при сомнениях |
| **Тулзы** | `read`, `grep`, `glob`; `Test-Path` (существование путей), `Get-FileHash` (рассинхрон копий), `git status` / `git diff`, `.venv\Scripts\python.exe` для проверочных скриптов; перепроверять выводы ревьюера (не доверять на слово) |
| **Фокус** | процесс + интеграция (не пере-ревьюить код — это сделал ревьюер) |
| **Выход** | вердикт `APPROVE` / `REQUEST_CHANGES` / `REJECT` + TD-* (если найдены) + `auditor_<ID>.json` |

### 3.4 Аналитик (analyst) — НОВОЕ ЗВЕНО

| Поле | Что дать |
|------|----------|
| **Роль** | систематизирует разрозненные находки ревьюера/аудитора, классифицирует и приоритизирует их, готовит «материал для работы» (сводку проблем, приоритеты, рекомендации по следующему блоку) для ресерчера и оркестратора |
| **Вход** | вердикты ревьюера + аудитора (текстом и JSON) + `docs/PROBLEMS_REGISTER.md` (актуальный, все TD-*) + спека блока (цитатой) + история блоков (что уже закрыто/запушено) |
| **МАТЕРИАЛ ДЛЯ РАБОТЫ** | см. `08_ANALYST_RESEARCHER_CONTRACT.md` §4. Если входа нет — «материал не найден, строить с нуля из артефактов» (`worker_<ID>.json`, `git log`) |
| **Скилы** | `adversarial-critic-checklist` (приоритизация находок по severity), `doubt-driven-development` (проверка обоснованности приоритетов) |
| **Тулзы** | `read`, `grep`, `glob` (сверка находок с реальными файлами), `git log` |
| **Выход** | сводка: классифицированные проблемы, приоритеты, рекомендации по следующему блоку → ресерчеру и оркестратору + `analyst_<ID>.json` |

### 3.5 Ресерчер (researcher) — НОВОЕ ЗВЕНО

| Поле | Что дать |
|------|----------|
| **Роль** | углублённое исследование: ищет в коде, БД сессий, легаси-документах и сети недостающее/неперенесённое, валидирует утверждения, дополняет материал фактами |
| **Вход** | сводка аналитика + `docs/PROBLEMS_REGISTER.md` + доступ к коду (`read`/`grep`/`glob`), БД сессий (sqlite, `.kanban.db`), легаси-документам (`E:\Documents`), git-истории |
| **МАТЕРИАЛ ДЛЯ РАБОТЫ** | см. `08_ANALYST_RESEARCHER_CONTRACT.md` §5. Если сводки аналитика нет — «материал не найден, исследовать с нуля», НЕ выдумывать факты |
| **Скилы** | `sources` — аудит источников/утверждений (что подтверждено, что нет, claim-level ledger); `verify` — проверка фактов с результатом pass/fail/not-tested |
| **Тулзы** | `read`, `grep`, `glob`, `git log`/`git diff`, sqlite (`.kanban.db`), `Test-Path`, сеть (webfetch / SearXNG) при необходимости |
| **Выход** | findings с доказательствами: что неперенесено/недостаёт, валидированные/опровергнутые утверждения → оркестратору + `researcher_<ID>.json` |

### 3.6 Деплоер (general по контракту 04)

| Поле | Что дать |
|------|----------|
| **Вердикты ОБОИХ** | ревьюер + аудитор; деплой ТОЛЬКО если оба `APPROVE` |
| **Список артефактов для коммита** | пути относительно корня portable (код/конфиг/скрипты, `reviewer_<ID>.json`, `auditor_<ID>.json`, `analyst_<ID>.json`, `researcher_<ID>.json`, `docs/PROBLEMS_REGISTER.md`, `.gitignore`) |
| **Контракт 04** | вставить `04_DEPLOYER_CONTRACT.md` полностью (включая шаг 3.5: `PROBLEMS_REGISTER.md` при наличии TD-*) |
| **Выход** | `DEPLOYED` / `BLOCKED` / `SKIPPED_NO_APPROVE` (по §4 контракта 04) |

## 4. ПРАВИЛА ПОСЛЕДОВАТЕЛЬНОСТИ

1. **НЕ запускать ревьюера и аудитора параллельно** — аудитор зависит от вердикта ревьюера. Только `worker → reviewer → auditor → analyst → researcher → deployer`. Аналитик и ресерчер тоже строго последовательны: ресерчер зависит от сводки аналитика.
2. Если ревьюер `REQUEST_CHANGES` — аудитор получает вердикт + причины. Аудитор может `APPROVE` (если `REQUEST_CHANGES` по коду не влияет на процесс/интеграцию) или вернуть воркеру.
3. Если ОБА `REQUEST_CHANGES` (или `REJECT`) — блок возвращается воркеру с **объединённым списком правок** (ревьюер + аудитор в одном списке, без дублей). Аналитик/ресерчер в этом случае НЕ запускаются до исправления.
4. Если ревьюер `APPROVE` И аудитор `APPROVE` → аналитик → ресерчер → деплоер.
5. Прикладывать файлы спецификаций **В КОНТЕКСТ** (цитировать секции), не только ссылаться — у субагентов нет доступа к диску в полном объёме.
6. Давать ФОКУС: «проверь ТОЛЬКО X, не уходи в Y» — субагенты склонны расширять scope. Формула: `Задача: <блок>. Фокус: <что проверять>. Вне фокуса: <что не трогать>.`
7. Каждый вердикт — файл-артефакт (`reviewer_<ID>.json`, `auditor_<ID>.json`): деплоер коммитит его как часть результата блока.
8. Техдолги фиксирует ТОТ, КТО НАШЁЛ (контракт 05), TD-ID перечисляются в вердикте.
9. **Аналитик/ресерчер идут ПОСЛЕ аудитора и ДО деплоера.** Деплой невозможен без их отработки: аналитик готовит материал, ресерчер дополняет фактами. Если аналитик/ресерчер нашли КРИТИЧНОЕ (пробел в фактах, неперенесённое, опровергнутое утверждение) — блок возвращается воркеру с объединённой сводкой (аналитик + ресерчер), как при `REQUEST_CHANGES`.
10. Сводка аналитика и findings ресерчера — файлы-артефакты (`analyst_<ID>.json`, `researcher_<ID>.json`), деплоер коммитит их как часть результата блока.
11. **Каждое звено обязано классифицировать свои находки по контракту 09 (уровни 1/2/3) — запрет замалчивания.** Нашёл проблему вне рамок задачи — НЕ «не обязан/не требуется», а обязательная классификация: (1) исправить сам, если ошибка в рамках задачи/целостности; (2) зафиксировать в отчёте секцией «НАХОДКИ (эскап-хэтч)» и при техдолге — в `PROBLEMS_REGISTER.md` (контракт 05); (3) эскалировать на следующий уровень при критичном/вне компетенции. Секция «НАХОДКИ (эскап-хэтч)» обязательна в отчёте каждого звена (см. контракт 09 §4).

## 5. МАТРИЦА КОНТЕКСТА (быстрая справка оркестратора)

| Звено | Обязательный контекст | Необязательный | Фокус |
|-------|----------------------|----------------|-------|
| worker | спека блока (цитатой), состояние файлов | полная картина (обзор трекера) | сделать по спеке, не выходить за scope |
| reviewer | спека блока (ПОЛНЫЙ текст), worker JSON, отчёт воркера, PROBLEMS_REGISTER, прошлые вердикты | смежные блоки (если влияют) | соответствие спеке + ложные отчёты + качество |
| auditor | вердикт reviewer (текстом), worker+reviewer JSON, спека блока, смежные, PROBLEMS_REGISTER, EXP-статус | прогноз интеграции | процесс + интеграция + перепроверка ревьюера |
| analyst | вердикты reviewer+auditor (текстом), PROBLEMS_REGISTER, спека блока, история блоков | детали кода (не нужны) | систематизировать находки, приоритеты, рекомендации |
| researcher | сводка аналитика, PROBLEMS_REGISTER, доступ к коду/БД/легаси/git | сеть (по необходимости) | найти недостающее/неперенесённое, валидировать утверждения |
| deployer | вердикты обоих (текстом), список артефактов | детали блока (не нужны) | коммит+push+TD (контракт 04) |

## 6. ЧТО ДЕЛАТЬ ПРИ ИСКЛЮЧЕНИЯХ

| Ситуация | Действие |
|----------|----------|
| Ревьюер `REJECT` (не `REQUEST_CHANGES`) | Блок возвращается воркеру СРАЗУ, аудитор не запускается до исправления. Вердикт + причины — воркеру. |
| Ревьюер `REQUEST_CHANGES`, аудитор `APPROVE` | Деплой НЕ выполняется (нужен APPROVE обоих). Правки по списку ревьюера → воркер → повторное ревью (аудит повторно не нужен, если процесс/интеграция не затронуты). |
| Оба `REQUEST_CHANGES` | Воркер получает объединённый список правок (без дублей) → повторный цикл. |
| Оба `APPROVE` | Аналитик → ресерчер → деплоер (контракт 04), статус `DEPLOYED`. |
| Аудитор не согласен с вердиктом ревьюера (`APPROVE` ревьюера, но аудитор `REJECT`) | Эскалация оркестратору: конфликт звеньев. НЕ деплоить. Оркестратор решает (может подключить третье мнение или трибунал). |
| Аналитик/ресерчер нашли КРИТИЧНОЕ (пробел, неперенесённое, опровергнутое утверждение) | Блок возвращается воркеру с объединённой сводкой (аналитик + ресерчер), как при `REQUEST_CHANGES`. |
| Ресерчер опроверг утверждение ревьюера/аудитора | Эскалация оркестратору (конфликт звеньев). НЕ деплоить до разрешения. |
| Материал аналитика неполон (нет вердикта, нет PROBLEMS_REGISTER) | Аналитик строит сводку из того, что есть (`worker_<ID>.json`, `git log`), неподтверждённое помечает `[UNVERIFIED]` — не выдумывает. |
| Воркер заявил DoD PASS, а ревьюер нашёл FAIL | Техдолг по контракту 05 (ложный отчёт) + возврат воркеру. |
| Нет вердикта одного из звеньев | Стоп до деплоя. Оркестратор дозапускает звено (не заменяет его додумыванием). |
| Артефакт звена не существует (путь не найден) | Не выдумывать замену. Зафиксировать и спросить воркера/оркестратора. |
| Спека блока изменилась во время цикла | Остановить цикл, перечитать актуальную секцию, перезапустить с воркера (старый контекст аннулирован). |
| 401 при push / отказ git-хука | По контракту 04 §6: `BLOCKED_NEED_WRITE_TOKEN` / исправить по сообщению хука, НЕ обходить. |

## 7. СВЯЗЬ С ДРУГИМИ КОНТРАКТАМИ

**Порядок использования (памятка оркестратору):**

1. Взял блок из `00_INDEX.md` §4 (критический путь).
2. Достал секцию спеки из `01`/`02`.
3. Запустил воркера (контекст §3.1) → получил артефакт + отчёт.
4. Запустил ревьюера (контекст §3.2 + контракт 05) → вердикт + `reviewer_<ID>.json`.
5. Запустил аудитора (контекст §3.3 + контракты 05/07 + ВЕРДИКТ РЕВЬЮЕРА) → вердикт + `auditor_<ID>.json`.
6. Запустил аналитика (контекст §3.4 + контракт 08) → сводка + `analyst_<ID>.json`.
7. Запустил ресерчера (контекст §3.5 + контракт 08 + сводка аналитика) → findings + `researcher_<ID>.json`.
8. При двух `APPROVE` и отсутствии критичных находок аналитика/ресерчера → деплоер (контракт 04 + список артефактов).
9. При `REQUEST_CHANGES`/`REJECT`/критичных находках → §4/§6 (возврат воркеру или эскалация).
