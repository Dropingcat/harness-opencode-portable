# 08_ANALYST_RESEARCHER_CONTRACT.md — Аналитик + Ресерчер в пайплайне

**Дата:** 2026-10-06 · **Статус:** АКТИВЕН · **Версия:** 1.0
**CWD:** `E:\opencode_harness_portable`

> Назначение: контракт для АНАЛИТИКА и РЕСЕРЧЕРА — двух последовательных звеньев пайплайна фабрики, работающих ПОСЛЕ аудитора и ДО деплоера. Оркестратор вставляет этот файл в промпт аналитику и ресерчеру после каждого завершённого блока, получившего `APPROVE` ревьюера и аудитора. Файл самодостаточен: правок при вставке не требуется.

---

## 1. РОЛЬ АНАЛИТИКА (после аудитора)

Аналитик — первое из двух новых звеньев. Он получает **разрозненные вердикты** ревьюера и аудитора (вместе с `PROBLEMS_REGISTER.md`, TD-*) и превращает их в **структурированный материал для работы** — сводку, по которой ресерчеру, оркестратору и (при необходимости) воркеру дальше работать.

Задачи аналитика:

1. **Систематизировать находки** ревьюера и аудитора: свести в единый список (без дублей), классифицировать (техдолг / баг / риск / пробел / несоответствие спеке).
2. **Классифицировать по severity:** critical / major / minor (шкала `adversarial-critic-checklist`), соотнести с TD-* из `PROBLEMS_REGISTER.md` и вердиктами.
3. **Приоритизировать:** что блокирует следующий блок, что можно отложить, что требует решения пользователя (`REQUIRES_USER_DECISION`).
4. **Подготовить рекомендации по следующему блоку** из критического пути (`00_INDEX.md` §4): на что смотреть ресерчеру, что проверить, какие утверждения валидировать.
5. **Проверить полноту материала:** если входа не хватает — строить сводку из того, что есть (`worker_<ID>.json`, `git log`), неподтверждённое помечать `[UNVERIFIED]`. НЕ выдумывать.

**Роль одной фразой:** превращает разрозненные находки ревью/аудита в структурированный отчёт (сводка + приоритеты + рекомендации) для исследователя и оркестратора.

## 2. РОЛЬ РЕСЕРЧЕРА (после аналитика)

Ресерчер — второе звено пары. Он получает **сводку аналитика** и проводит **углублённое исследование** для полноты картины: ищет недостающее и неперенесённое, валидирует утверждения, дополняет материал фактами.

Задачи ресерчера:

1. **Исследовать по источникам:** код (`read`/`grep`/`glob`), БД сессий (sqlite — `.kanban.db`, `.l2_memory/`), легаси-документы (`E:\Documents`), git-историю (`git log`/`git diff`), при необходимости — сеть (webfetch / SearXNG).
2. **Найти недостающее/неперенесённое:** что заявлено в спеке/вердиктах, но отсутствует в коде/артефактах/дереве; что есть в каноне/легаси, но не перенесено в portable.
3. **Валидировать утверждения** ревьюера, аудитора и аналитика: каждое проверяется фактами (скил `verify` → pass/fail/not-tested). Утверждение без доказательства — `[UNVERIFIED]`, НЕ принимается на веру.
4. **Аудировать источники** (скил `sources`): claim-level ledger — откуда взято каждое утверждение, подтверждено ли первичным источником, есть ли контракт/документ/файл.
5. **Дополнить материал фактами:** результат — findings с доказательствами (пути, команды, номера TD), что именно неперенесено/недостаёт и что с этим делать.

**Роль одной фразой:** углублённое исследование (код, БД сессий, легаси-документы, сеть) для полноты картины и проверки фактов перед деплоем.

## 3. ПОСЛЕДОВАТЕЛЬНОСТЬ (полный цикл блока)

```
worker → reviewer → auditor → analyst → researcher → deployer
```

- **Аналитик** запускается ТОЛЬКО после `APPROVE` ревьюера И аудитора (правило 06 §4.4).
- **Ресерчер** запускается ТОЛЬКО после сводки аналитика — он зависит от неё (правило 06 §4.1).
- **Деплоер** запускается ТОЛЬКО после отработки обоих, ЕСЛИ аналитик/ресерчер не нашли критичного.
- Если аналитик/ресерчер нашли **критичное** (пробел в фактах, неперенесённое, опровергнутое утверждение) — блок возвращается воркеру с объединённой сводкой (правило 06 §4.9), повторный цикл.
- Параллельный запуск аналитика и ресерчера — НЕ штатный режим (ресерчер без сводки аналитика начинает с нуля).

## 4. МАТЕРИАЛ ДЛЯ АНАЛИТИКА (что прикладывает оркестратор)

Оркестратор прикладывает в промпт аналитика **текстом (цитатами)**, не ссылками:

| Поле | Что приложить |
|------|---------------|
| **PROBLEMS_REGISTER.md** | актуальный, со ВСЕМИ TD-* (не только из этого блока) |
| **Вердикты ревьюера/аудитора** | текст вердиктов + `reviewer_<ID>.json` + `auditor_<ID>.json` |
| **Спека блока** | текст секции `B*-T*` / `W*` (прикладывать цитатой, как воркеру/ревьюеру) |
| **История блоков** | что уже закрыто/запушено (`git log --oneline`, статусы из трекера) |
| **Контракт 05** | для корректной работы с TD-* (`05_REVIEWER_AUDITOR_TECHDEBT.md`) |

**Если чего-то из этого нет** — аналитик фиксирует «материал не найден, строить с нуля из артефактов» (`worker_<ID>.json`, `git log`, фактические файлы блока). Не выдумывать отсутствующие вердикты или TD.

**Скилы аналитика:** `adversarial-critic-checklist` (структурированная приоритизация находок по severity), `doubt-driven-development` (обоснованность приоритетов).

**Тулзы аналитика:** `read`, `grep`, `glob` (сверка находок с реальными файлами), `git log`.

## 6. КОНТРАКТ ВЫХОДА

### 6.1 Аналитик возвращает

Сводку (в `analyst_<ID>.json` + текстом оркестратору):

| Секция | Содержимое |
|--------|------------|
| **Сводка** | единый список найденных проблем (без дублей) с классификацией: техдолг / баг / риск / пробел / несоответствие спеке |
| **Приоритеты** | critical / major / minor (соответствие TD-* и вердиктам); что блокирует следующий блок, что отложить, что `REQUIRES_USER_DECISION` |
| **Рекомендации** | по следующему блоку из критического пути: на что смотреть ресерчеру, что проверить, какие утверждения валидировать |
| **Вопросы для ресерчера** | формализованный клубок (по 10 §4): почему? откуда? как? что лучше? |
| **Материал** | что приложено оркестратором; если чего-то не хватало — пометка `[UNVERIFIED]` + откуда строил (`worker_<ID>.json`, `git log`) |

**Обязательное требование к отчёту аналитика:**
- Отчёт аналитика ОБЯЗАН содержать: сводку вердиктов, классификацию TD, приоритеты для ресерчера, рекомендации для оркестратора, «вопросы» для ресерчера (по 10 §4).
- Отчёт сохраняется в `.runs/artifacts/<ID>/analyst_<ID>.json` + строка в `ANALYST_REPORTS.md` (делает деплоер по 04 §3.6).

### 6.2 Ресерчер возвращает

Findings (в `researcher_<ID>.json` + текстом оркестратору):

| Секция | Содержимое |
|--------|------------|
| **Findings** | список того, что неперенесено/недостаёт, с ДОКАЗАТЕЛЬСТВАМИ (пути, команды, номера TD) |
| **Валидация** | каждое утверждение ревьюера/аудитора/аналитика → pass / fail / not-tested |
| **Ledger источников** | откуда взято каждое утверждение (код / БД / легаси / git / сеть), подтверждено ли первичным источником |
| **Рекомендации** | что с этим делать: вернуть воркеру (критично) / зафиксировать TD / отложить |

### 6.3 ПУТЬ АРТЕФАКТА (обязательный шаблон)

```
${HARNESS_ROOT}/<ROLE>_<BLOCK_ID>.json
Пример: E:\opencode_harness_portable\analyst_W1.json, E:\opencode_harness_portable\researcher_EXP-1b.json
```

- HARNESS_ROOT = `E:\opencode_harness_portable` (НЕ `.runs/` — это рантайм, не версионируется)
- ROLE = `worker` | `reviewer` | `auditor` | `analyst` | `researcher` | `deployer`
- BLOCK_ID = идентификатор блока (B1-T2, W1, EXP-1b...)
- Файл git-версионируется (деплоер коммитит)
- Отчёт в отчёте: указывать путь явно
- Отчёты аналитика/ресерчера (`analyst_<ID>.json`, `researcher_<ID>.json`) записывать ПО ЭТОМУ шаблону в HARNESS_ROOT (в `.runs/artifacts/` — только рантайм-копии, не источник)
