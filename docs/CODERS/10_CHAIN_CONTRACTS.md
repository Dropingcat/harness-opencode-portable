> Назначение: УТОЧНЁННЫЕ контракты звеньев по запросу пользователя — детальные требования к ВХОДНЫМ ДАННЫМ по всей цепочке. ## 1. ПРИНЦИП ПОТОКА (как информация движется по цепочке)

```
worker → reviewer → auditor → analyst → researcher → deployer
```

Каждое звено получает НЕ только результат, а ВЕСЬ контекст: **что было, что стало, что заявлялось, что проверялось**. Контекст передаётся НАКОПИТЕЛЬНО — каждое следующее звено видит все артефакты и вердикты предыдущих, но НИ ОДНО звено не принимает их на веру.

**Правила потока:**
1. **Накопление, не замена:** ревьюеру прикладывается отчёт воркера, аудитору — отчёт воркера + вердикт ревьюера, аналитику — всё + оба вердикта, ресерчеру — всё + сводка аналитика, деплоеру — всё + вердикты.
2. **Недоверие на каждом шаге:** каждый агент ПРОВЕРЯЕТ вход фактами (файлы, команды), не верит отчётам предыдущих звеньев на слово (07 §3.3: «не верь отчётам, верь файлам»).
3. **Артефакт каждого звена** (`worker_<ID>.json`, `reviewer_<ID>.json`, `auditor_<ID>.json`, `analyst_<ID>.json`, `researcher_<ID>.json`) — часть результата блока, коммитится деплоером (контракт 04, шаг 3.5).
4. **Классификация находок** — контракт 09 (уровни 1/2/3) обязателен для КАЖДОГО звена (06 §4.11), секция «НАХОДКИ (эскап-хэтч)» — в конце каждого отчёта.
5. **Техдолги TD-*** — контракт 05: фиксирует ТОТ, КТО НАШЁЛ, в `docs/PROBLEMS_REGISTER.md`.
6. **ПУТЬ АРТЕФАКТА (обязательный шаблон)** — каждый выход-файл звена записывается по шаблону `${HARNESS_ROOT}/<ROLE>_<BLOCK_ID>.json` (см. §9). Не писать вердикты/сводки БЕЗ явного пути в корень workspace.

## 2. РЕВЬЮЕР (входные данные)

### Что получает

| Поле | Что прикладывает оркестратор |
|------|------------------------------|
| **ТЗ (tech task)** | что было написано в задаче ДОСЛОВНО (спека блока цитатой, ПОЛНЫЙ текст секции `B*-T*` / `W*`) |
| **«Всю телегу»** | что было (baseline/до), что стало (diff/результат) — `git status` / `git diff` / `read` затрагиваемых файлов; отчёт воркера (заявленные DoD) |
| **Легаси-документацию** | `docs/PROBLEMS_REGISTER.md` (актуальные TD-*), историю блоков, прошлые вердикты по этому блоку (если `REQUEST_CHANGES` ранее — что уже просили исправить) |
| **Артефакты воркера** | `worker_<ID>.json` или изменённый файл — проверяет, не доверяет |
| **Контракты** | 05 (TD-формат), 06 §3.2, 09 (эскап-хэтч) |

**Если материала нет** — зафиксировать «материал не найден, проверять с нуля», НЕ выдумывать (06 §3.2).

### Что делает

1. **Сравнивает «было → стало» с ТЗ:** каждое требование спеки → факт (требование → что реально в файле/артефакте).
2. **Делает ОБЗОР выполненного** (презентация): «это сделано, вот как это бьётся с задачей» — структурированный разбор, каждый пункт спеки закрыт/не закрыт.
3. **Ищет ложные отчёты** (DoD PASS но FAIL), несоответствия спеке, пропущенное.

### Скилы
`adversarial-critic-checklist` (обязательный — 6 проверок, severity critical/major/minor), `review` (evidence-backed findings), `doubt-driven-development` (сомнения в нетривиальных решениях).

### Тулзы
`read`, `grep`, `glob`, `git status` / `git diff` — проверка по фактам, не верить отчёту воркера на слово.

### Выход
Вердикт `APPROVE` / `REQUEST_CHANGES` / `REJECT` + TD-* (по 05) + «обзор выполненного» + `reviewer_<ID>.json`.

## 3. АУДИТОР (входные данные)

### Что получает

| Поле | Что прикладывает оркестратор |
|------|------------------------------|
| **Отчёты ревьюера** | его «презентацию» о том что сделано и как бьётся с задачей — НО НЕ ДОВЕРЯЕТ |
| **Артефакты, которые ревьюер проверял** | `worker_<ID>.json` + `reviewer_<ID>.json` — проверяет САМ (перепроверка) |
| **Спека блока + смежные блоки** | текст секции блока + зависимости (что идёт дальше, что блокирует — из `00_INDEX.md` §4, `01`, `02`) + EXP-статус (какие EXP-протоколы подтверждены/нужны) |
| **Контракты** | 05 (TD-формат), 06 §3.3, 07 (въедливость — обязателен), 09 (эскап-хэтч) |

**Если материала нет** — «материал не найден, проверять с нуля» (не выдумывать).

### ПРИНЦИП: «Аудитор вообще НЕ верит никому — он знает, что его все обманывают»

1. **Каждое утверждение ревьюера/воркера → перепроверка ФАКТАМИ** (07 §3.3: не верь отчётам, верь файлам). Вердикт ревьюера — входной факт, а не догма (07 §5).
2. **Артефакты: проверяет ИХ СУЩЕСТВОВАНИЕ И СОДЕРЖИМОЕ** (`Test-Path` + read), не доверяет тому что в них написано.
3. **Ищет:** ложные PASS, непроверенные утверждения, скрытые проблемы, рассинхроны. Триггеры копания — контракт 07 §2 (14 триггеров).

### Скилы
`ariz-contradiction-resolution` (противоречия вердиктов — 8 шагов), `verify` (реальные проверки → pass/fail/not-tested), `doubt-driven-development`, 07 (въедливость).

### Тулзы
`read`, `grep`, `glob`; `Test-Path`, `Get-FileHash`, `git status` / `git diff`, `.venv\Scripts\python.exe` для проверочных скриптов.

### Выход
Вердикт `APPROVE` / `REQUEST_CHANGES` / `REJECT` + TD-* + **секция 0 «Сомнительное, что я проверил»** (обязательна, перед вердиктом — 07 §6) + `auditor_<ID>.json`.

## 4. АНАЛИТИК (входные данные)

### Что получает

| Поле | Что прикладывает оркестратор |
|------|------------------------------|
| **Вердикты ревьюера и аудитора** | оба (текстом + JSON) |
| **PROBLEMS_REGISTER** | актуальный, ВСЕ TD-* |
| **Спека блока + история блоков** | текст секции `B*-T*` / `W*` (цитатой) + что уже закрыто/запушено (`git log --oneline`, статусы трекера) |
| **Контракты** | 05 (работа с TD), 06 §3.4, 08 §4, 09 (эскап-хэтч) |

**Если входа нет** — «материал не найден, строить с нуля из артефактов» (`worker_<ID>.json`, `git log`), неподтверждённое помечать `[UNVERIFIED]`, НЕ выдумывать (06 §3.4, 08 §4).

### Что делает (по запросу пользователя)

1. **Находит ЧТО НЕ СООТВЕТСТВУЕТ документации** (архитектурные/кодовые блоки/мелкие помарки): систематизирует разрозненные находки ревьюера/аудитора в единый список без дублей, классифицирует (техдолг / баг / риск / пробел / несоответствие спеке).
2. **РАСКРУЧИВАЕТ КЛУБОК:** берёт несоответствия и ФОРМАЛИЗУЕТ их для ресерчера в ВОПРОСЫ и ЗАДАЧИ — превращает сырые находки в конкретные исследовательские вопросы.
3. **Готовит «вопросы»** (почему? откуда? как? что лучше?) по каждому несоответствию.
4. Классифицирует по severity (critical/major/minor), приоритизирует (что блокирует следующий блок, что отложить, что `REQUIRES_USER_DECISION`).

### Скилы
`adversarial-critic-checklist` (приоритизация по severity), `doubt-driven-development` (обоснованность приоритетов).

### Тулзы
`read`, `grep`, `glob`, `git log`.

### Выход
Сводка (классифицированные проблемы + приоритеты + рекомендации по следующему блоку) + **ПЕРЕЧЕНЬ ВОПРОСОВ ДЛЯ РЕСЕРЧЕРА (формализованный клубок)** + `analyst_<ID>.json`.

## 5. РЕСЕРЧЕР (входные данные)

### Что получает

| Поле | Что прикладывает оркестратор |
|------|------------------------------|
| **ВОПРОСЫ от аналитика** | почему? откуда? как? что лучше? (формализованный клубок) |
| **PROBLEMS_REGISTER + сводку аналитика** | актуальный реестр + текст сводки + `analyst_<ID>.json` |
| **Доступ** | код (`read`/`grep`/`glob`), БД сессий (sqlite: `.kanban.db`, при наличии `.l2_memory/`), легаси-документы (`E:\Documents`), git-история (`git log`/`git diff`), сеть (webfetch / SearXNG) при необходимости |
| **Контракты** | 08 §5, 09 (эскап-хэтч) |

**Если сводки аналитика нет** — «материал не найден, исследовать с нуля», НЕ выдумывать факты (06 §3.5, 08 §5).

### Что делает

1. **ОТВЕЧАЕТ на вопросы аналитика с доказательствами** (пути/команды/выводы) — каждый ответ подтверждён фактом.
2. **Копает глубже:** «почему так?», «откуда это?», «как это работает?», «что лучше?» — находит недостающее/неперенесённое.
3. **Валидирует утверждения всех предыдущих звеньев** (`sources` — claim-level ledger, `verify` → pass/fail/not-tested). Утверждение без доказательства — `[UNVERIFIED]`, не принимается на веру.

### Скилы
`sources` (аудит источников, claim-level ledger), `verify` (реальные проверки → pass/fail/not-tested).

### Тулзы
`read`, `grep`, `glob`, `git log`/`git diff`, sqlite (`.kanban.db`), `Test-Path`, сеть (webfetch / SearXNG) при необходимости.

### Выход
Findings с verdict (pass/fail/not-tested) по каждому вопросу аналитика + новые находки (что неперенесено/недостаёт, с доказательствами — пути/команды/TD) + рекомендации + `researcher_<ID>.json`.

## 7. ВРЕМЕННЫЕ ФАЙЛЫ (решение пользователя)

- **Временные файлы разработки создавать в `E:\opencode_harness_portable\.runs\artifacts\`** (НЕ в `C:\Temp` — он не трекается и теряется).
- **Правило:** любой промежуточный артефакт (freeze, delta, дампы) → `.runs\artifacts\<блок>\` с именем `<ID>_<описание>.txt` (например `B1-T1_venv_delta.txt`).
- **`.runs/` уже в `.gitignore`** (не утекает в git), но доступен всем звеньям пайплайна.
- **Если `.runs/artifacts` не создан — создать** (это и есть temp для разработки). Создаётся воркером при старте блока.

## 9. ПУТЬ АРТЕФАКТА (обязательный шаблон, все звенья)

```
${HARNESS_ROOT}/<ROLE>_<BLOCK_ID>.json
Пример: E:\opencode_harness_portable\reviewer_EXP-1b.json, E:\opencode_harness_portable\auditor_W1.json
```

- HARNESS_ROOT = `E:\opencode_harness_portable` (НЕ `.runs/` — это рантайм, не версионируется)
- ROLE = `worker` | `reviewer` | `auditor` | `analyst` | `researcher` | `deployer`
- BLOCK_ID = идентификатор блока (B1-T2, W1, EXP-1b...)
- Файл git-версионируется (деплоер коммитит)
- Отчёт в отчёте: указывать путь явно
- Применяется к: `worker_<ID>.json`, `reviewer_<ID>.json`, `auditor_<ID>.json`, `analyst_<ID>.json`, `researcher_<ID>.json` и любым другим выходным JSON звеньев. В `.runs/artifacts/` — только рантайм-копии, не источник.
- **Для проектов** — `${HARNESS_ROOT}/projects/<PROJECT_ID>/artifacts/<ROLE>_<BLOCK_ID>.json` (контракт 12). Каждый НОВЫЙ проект = отдельная директория артефактов с единообразными правилами/переменными (масштабирование без коллизий, см. `12_PROJECT_ARTIFACTS.md`).
