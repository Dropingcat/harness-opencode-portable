> Назначение: контракт выбора агентов для каждой роли пайплайна `worker → reviewer → auditor → analyst → researcher → deployer`. Основан на исследовании стека агентов (`.runs/artifacts/agents-stack/agents_research.md`, 2026-10-07): какой агент КАКОГО типа использовать на какой роли, что оркестратор обязан добавить в промпт спец-агентам (конвертер вердиктов, мост TD, эскап-хэтч 09), и когда переключаться на fallback. ## 1. ТЕКУЩИЙ ПАЙПЛАЙН (worker → reviewer → auditor → analyst → researcher → deployer)

Какая роль → какой агент (тип task) и через что вызывается:

```
worker → reviewer → auditor
        → analyst:    synthesizer (через synthesizer-runner, TD-099)
                      └─ claim-parser — ОПЦИОНАЛЬНЫЙ суб-шаг «раскрутки клубка»
                      └─ fallback: general (по контракту 08)
        → researcher: general (по контракту 08 §5) — каналы код/БД/легаси/git
                      └─ суб-звенья (внешне-научный канал, через runner-обёртки):
                         source-fetcher → fact-checker
                      └─ fallback: general без суб-звеньев
        → deployer:   general (по контракту 04)
```

- **worker → reviewer → auditor → deployer** — без изменений: `coder-worker`, `code-reviewer`, `code-auditor`, `general` (04 §3.6, 06 §3.6).
- **analyst** — меняется с `general` на `synthesizer` (лучший кандидат из исследования), `general` остаётся fallback.
- **researcher** — остаётся `general` как ядро (код/БД/легаси/git — НЕ покрыто спец-агентами), к нему добавляется пара суб-звеньев `source-fetcher → fact-checker` для внешне-научных вопросов.
- **research-orchestrator** — НЕ звено пайплайна, а хост для запуска пары `source-fetcher → fact-checker` через runner-обёртки (TD-099).
- **W9 peer-координация** (`peer_coordinator.py`) недоступна до M2 (T4 BLOCKED) → конфликт звеньев решается эскалацией оркестратору (06 §6), не трибуналом.

**Суб-шаг/суб-звенья (не самостоятельные роли):**

| Суб-агент | Кому подчинён | Когда вызывать | Выход |
|---|---|---|---|
| `claim-parser` | аналитику (суб-шаг) | когда клубок находок надо разбить на атомарные утверждения перед сведением без дублей | `claims.json` |
| `source-fetcher` | ресерчеру (суб-звено) | когда вопрос аналитика требует внешних источников/статей (не кода/БД) | `sources_<id>.json` |
| `fact-checker` | ресерчеру (суб-звено, ПОСЛЕ source-fetcher) | когда утверждение надо сравнить с уже найденными источниками | verdicts (SUPPORTED/CONTRADICTED/UNSUPPORTED/AMBIGUOUS) |

**НЕ использовать как звенья:** `tribunal-judge` (перебор для аналитика), `claim-parser` (только суб-шаг), `research-orchestrator` (хост, не звено), `researcher` (отключён, `disable: true`), `explore` (инструмент, не роль).

## 3. АНАЛИТИК = SYNTHESIZER (интеграция)

### Что synthesizer даёт аналитику

- Вход `verdicts_final.json` ≈ вход аналитика (разрозненные вердикты ревьюера/аудитора) — почти 1-в-1.
- Выход: структурированный отчёт с **проблемными тезисами** и **`questions_for_author`** — это прямое сырьё для «Вопросов для ресерчера» из 08 §6.1 (переименовать `questions_for_author` → `questions_for_researcher`).
- Встроенная честность (анти-сикофантия) = принцип «не выдумывать» + `[UNVERIFIED]` из 08.

### ЧТО ДОБАВИТЬ в промпт synthesizer-аналитику (добавляет оркестратор)

Оркестратор вставляет в промпт синтезатора ВМЕСТЕ с контрактом 08/10 следующие 4 блока:

**1. Конвертер формата вердиктов (обязательно, блокер без него).**
Фабричные вердикты `APPROVE`/`REQUEST_CHANGES`/`REJECT` ≠ синтезаторные `SUPPORTED`/`CONTRADICTED`/`UNSUPPORTED`/`AMBIGUOUS`. Оркестратор даёт маппинг текстом:
```
Вердикты фабрики трактуй так:
  APPROVE          → SUPPORTED      (находок/опровержений нет, подтверждено)
  REQUEST_CHANGES  → CONTRADICTED   (есть конкретное несоответствие спеке/коду)
                  → AMBIGUOUS       (несоответствие неоднозначно/нужна проверка)
  REJECT           → UNSUPPORTED    (работа не подтверждена, требует переделки)
Каждый вердикт ревьюера/аудитора + его TD-* → claim_id (свой), verdict, confidence,
caveats, sources_used (пути файлов). PROBLEMS_REGISTER.md подаётся как источники.
```
Если оркестратор имеет готовый конвертер `reviewer_<ID>.json`+`auditor_<ID>.json` → `verdicts_final.json` — использовать его, иначе маппинг текстом (выше).

**2. Контракт 05 (TD-фиксация) — мост.**
```
Найденные техдолги (TD-*) НЕ регистрируй в PROBLEMS_REGISTER.md сам,
если твой контракт не предусматривает записи в реестр.
Верни оркестратору ОТДЕЛЬНЫЙ список TD: [{td_id, severity, what, comment, block}].
Оркестратор зарегистрирует их в PROBLEMS_REGISTER.md по контракту 05.
```
Правило 05 «фиксирует тот, кто нашёл» выполняется через мост: синтезатор находит и формулирует → оркестратор (или деплоер по 04 шаг 3.6) физически пишет в реестр.

**3. Контракт 09 (эскап-хэтч) — секция в конце.**
```
Секция «НАХОДКИ (эскап-хэтч)» ОБЯЗАТЕЛЬНА в конце твоего отчёта
(уровни 1/2/3 по контракту 09; если находок не было — написать «находок не было»).
Пустая секция без явной пометки = красный флаг.
```

**4. Формат выхода (по 08 §6.1 + 10 §4).**
```
Сводка: единый список проблем без дублей + классификация (техдолг/баг/риск/пробел/несоответствие спеке)
       + severity (critical/major/minor, шкала adversarial-critic-checklist).
Приоритеты: что блокирует следующий блок / что отложить / что REQUIRES_USER_DECISION.
Рекомендации по следующему блоку (00_INDEX §4).
Вопросы для ресерчера: из questions_for_author → why/where/how/what-better (по 10 §4).
Материал: что приложено; если чего-то не хватало — [UNVERIFIED] + откуда строил.
Сохрани результат: .runs/artifacts/<ID>/analyst_<ID>.json (или верни JSON оркестратору — он сохранит).
```

### Fallback: general

Если synthesizer недоступен/не подходит (вход не в формате вердиктов, сбой обёртки, нет конвертера) — **`general` по текущему контракту 08** (текущее поведение, работает). Переключение решает оркестратор; в отчёте фиксируется какой агент использован.

## 4. РЕСЕРЧЕР = GENERAL + СУБ-ЗВЕНЬЯ (интеграция)

**Два режима ресерчера — см. контракт 16 (`16_RESEARCH_MINI_FACTORY.md`):** DEEP (мини-фабрика: research-orchestrator BRICKS-runner + внешний аудитор режим B + ТРИЗ-ветка) для внешне-научных задач и LIGHT (general-ядро, без полного цикла) для локальных вопросов. Оркестратор классифицирует DEEP/LIGHT при диспатче (16 §2/§8).

### Ядро: general

Отвечает на вопросы аналитика (почему? откуда? как? что лучше?) с доказательствами. Каналы (08 §5, 10 §5):
- **код** — `read`/`grep`/`glob` по `E:\opencode_harness_portable`;
- **БД сессий** — sqlite: `.kanban.db`, при наличии `.l2_memory/` (только чтение);
- **легаси** — `E:\Documents\Документы\doc_Opencode_agern-new` и канон-справочники (только чтение);
- **git-история** — `git log`/`git diff`/`git branch -a`;
- **сеть** — webfetch / SearXNG (при необходимости; для глубокого внешне-научного поиска — см. суб-звенья);
- **валидация** — скилы `verify` (pass/fail/not-tested), `sources` (claim-level ledger).

### Суб-звенья (опционально, только внешне-научный канал)

| Суб-звено | Что делает | Вход | Выход |
|---|---|---|---|
| `source-fetcher` | поиск источников по теме → trust-ранжирование, provenance, rejected_sources | ResearchTask (claim_ids/claim_texts/question) | `sources_<id>.json` |
| `fact-checker` | сравнение утверждения с источниками → verdict + confidence + caveats | `claims.json` + `sources_<id>.json` | verdicts (SUPPORTED/CONTRADICTED/UNSUPPORTED/AMBIGUOUS) |

**Когда вызывать:** если вопросы аналитика касаются ВНЕШНИХ фактов/источников (статьи, научные данные, документы), а не кода/БД/легаси. Решает **оркестратор** (при диспатче ресерчера помечает «внешний канал требуется»), либо сам general-ресерчер через `task` (диспатч runner-обёрток по TD-099).

**Порядок:** строго `source-fetcher` → `fact-checker` (без найденных источников fact-checker не работает). Запуск — через runner-обёртки (`source-fetcher-runner` → `fact-checker-runner`) или `research-orchestrator` как хост.

**Переработка в findings:** ресерчер берёт `sources_<id>.json` + verdicts факт-чекера и перерабатывает в `researcher_<ID>.json`: verdict fact-checker `SUPPORTED/CONTRADICTED/UNSUPPORTED` ≡ `pass/fail/not-tested` (08 §6.2); ledger источников — из `sources_<id>.json` (provenance/trust).

### Мост TD/09 (обязательный для суб-звеньев)

Суб-звенья НЕ фиксируют TD (факт-чекер `edit: deny`, их контракты не знают 05/09) и НЕ имеют секции эскап-хэтча.
- **TD:** ресерчер собирает находки суб-звеньев и либо регистрирует их сам в `PROBLEMS_REGISTER.md` (по 05), либо возвращает оркестратору список TD для регистрации. НЕ оставлять находки суб-звеньев без TD-фиксации.
- **09:** оркестратор добавляет секцию «НАХОДКИ (эскап-хэтч)» в промпт ресерчеру (включая инструкцию «включи находки суб-звеньев source-fetcher/fact-checker в эту секцию»).
- **Конфликт звеньев** (ресерчер опроверг утверждение ревьюера/аудитора) — эскалация оркестратору (06 §6), НЕ деплой до разрешения (W9 peer-координация до M2 недоступна).

## 5. ЧТО НЕ МЕНЯЕТСЯ

- **Воркер/ревьюер/аудитор/деплоер** — по контрактам 04–07: `coder-worker`, `code-reviewer`, `code-auditor`, `general` (04 §3.6). Промпты и контракты выхода без изменений.
- **Порядок пайплайна** — строго `worker → reviewer → auditor → analyst → researcher → deployer` (06 §2); аналитик/ресерчер строго последовательны.
- **Процессная дисциплина** (TD по 05, эскалация по 09, артефакты `*_<ID>.json`) — обязательна для ВСЕХ звеньев, включая спец-агентов (через мост оркестратора — см. §3/§4).
- **Артефакты:** `analyst_<ID>.json` и `researcher_<ID>.json` — часть результата блока, коммитит деплоер (04 шаг 3.5); отчёт аналитика → журнал `ANALYST_REPORTS.md` (04 шаг 3.6).
- **ПУТЬ АРТЕФАКТА (обязательный шаблон):** каждый выход-файл звена записывается по шаблону `${HARNESS_ROOT}/<ROLE>_<BLOCK_ID>.json` (см. ниже).
- **Недоверие на каждом шаге** (10 §1): агент проверяет вход фактами, не верит отчётам предыдущих звеньев.

### 5.1 ПУТЬ АРТЕФАКТА (обязательный шаблон)

```
${HARNESS_ROOT}/<ROLE>_<BLOCK_ID>.json
Пример: E:\opencode_harness_portable\reviewer_EXP-1b.json, E:\opencode_harness_portable\auditor_W1.json
```

- HARNESS_ROOT = `E:\opencode_harness_portable` (НЕ `.runs/` — это рантайм, не версионируется)
- ROLE = `worker` | `reviewer` | `auditor` | `analyst` | `researcher` | `deployer`
- BLOCK_ID = идентификатор блока (B1-T2, W1, EXP-1b...)
- Файл git-версионируется (деплоер коммитит)
- Отчёт в отчёте: указывать путь явно
- Спец-агенты (synthesizer, source-fetcher, fact-checker) возвращают результат оркестратору/ресерчеру, тот сохраняет по шаблону; в `.runs/artifacts/` — только рантайм-копии, не источник.

## 6. РИСКИ И FALLBACK

| Риск | Митигация |
|---|---|
| **Синтезатор не в формате фабрики** (вердикты `APPROVE/REQUEST_CHANGES/REJECT` + TD-* vs `SUPPORTED/...`) | Конвертер: маппинг текстом в промпте (см. §3 п.1) или готовый конвертер оркестратора → `verdicts_final.json`. Без него — fallback на `general`. |
| **Спец-агент не пишет TD** (синтезатор не знает 05, факт-чекер `edit: deny`) | Мост: агент возвращает список TD оркестратору/ресерчеру, они регистрируют в `PROBLEMS_REGISTER.md` по 05; деплоер страхует на шаге 3.6 (04). |
| **Спец-агент не имеет эскап-хэтча 09** | Оркестратор вставляет секцию «НАХОДКИ (эскап-хэтч)» в промпт каждому звену (06 §4.11) и проверяет её наличие в отчёте. |
| **Недоступность агента / сбой runner-обёртки** | Fallback: аналитик → `general` (08), ресерчер → `general` без суб-звеньев (08 §5). Сбой фиксируется в отчёте. |
| **Конфликт форматов на входе** (`reviewer_<ID>.json`/`auditor_<ID>.json` ≠ `verdicts_final.json`) | Конвертер; если конвертации нет — `general` по 08 (строит сводку из того, что есть, `[UNVERIFIED]`). |
| **Вопросы аналитика не покрыты спец-агентами** (код/БД/легаси/git) | Эти каналы всегда ведёт `general` (ядро ресерчера); суб-звенья — ТОЛЬКО внешне-научный канал. |
| **W9 peer-координация недоступна (T4 BLOCKED, до M2)** | Конфликт звеньев → эскалация оркестратору (06 §6), трибунал/peer-координацию не запускать. |
| **Синтезатор не классифицирует TD/severity** | Контракт-расширение в промпте (§3 п.4): шкала `adversarial-critic-checklist`, TD-формат по 05 — задаётся оркестратором явно. |
