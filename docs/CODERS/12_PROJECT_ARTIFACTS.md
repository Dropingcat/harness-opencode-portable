# 12_PROJECT_ARTIFACTS.md — Директория артефактов проекта (масштабирование фабрики)
**Дата:** 2026-10-07 · **Статус:** АКТИВЕН · **Версия:** 1.0

## 1. ЦЕЛЬ
При старте НОВОГО проекта фабрика создаёт ОТДЕЛЬНУЮ директорию артефактов проекта с единообразными правилами/переменными. Масштабирование: новые проекты, артефакты, агенты — без коллизий и потерь.

## 2. СТРУКТУРА ДИРЕКТОРИИ ПРОЕКТА
${HARNESS_ROOT}/projects/<PROJECT_ID>/
├── artifacts/          # артефакты звеньев: <ROLE>_<BLOCK_ID>.json (git-версионируется)
├── runs/               # рантайм (.runs-аналог, НЕ в git)
├── reports/            # ANALYST_REPORTS, ORCHESTRATOR_NOTES проекта
├── tech_debt.md        # TD-реестр проекта (или ссылка на общий)
├── README.md           # PROJECT_ID, цель, переменные, правила
└── config.env          # переменные проекта (см. §4)

Где PROJECT_ID — kebab-case (например: my-client-v2, research-llm-audit).

## 3. ПРАВИЛА (единообразные)
- Каждый проект = отдельная директория (никакого смешения артефактов разных проектов).
- Артефакты: <ROLE>_<BLOCK_ID>.json по шаблону (контракт 10 §9), лежат в projects/<PROJECT_ID>/artifacts/.
- Верификация: единые DoD-проверки (контракты 03-05), не зависящие от проекта.
- Рантайм (.runs/, .meta_state/, временные) — в projects/<PROJECT_ID>/runs/, НЕ в git.
- Отчёты аналитика/журналы — в projects/<PROJECT_ID>/reports/ (или ссылки на общий журнал с указанием проекта).

## 4. ПЕРЕМЕННЫЕ (единообразные, переопределяются в config.env проекта)
| Переменная | Дефолт (harness) | Проект |
|---|---|---|
| HARNESS_ROOT | E:\opencode_harness_portable | (не меняется) |
| PROJECT_ID | — | my-client-v2 |
| PROJECT_ARTIFACTS | ${HARNESS_ROOT}/projects/<PROJECT_ID>/artifacts | то же |
| PROJECT_RUNS | ${HARNESS_ROOT}/projects/<PROJECT_ID>/runs | то же |
| PROJECT_REPORTS | ${HARNESS_ROOT}/projects/<PROJECT_ID>/reports | то же |
| OPENCODE_MODEL | (пользовательский выбор) | переопределяется по проекту |
| OPENCODE_HARNESS_ROOT | (harness) | (не меняется) |

Переменные проекта экспортируются в setup_env.ps1 (если запуск внутри проекта) или в промптах звеньев.

## 5. МАСШТАБИРОВАНИЕ
- Новый проект = mkdir projects/<PROJECT_ID> + config.env (одна команда/скрипт — предложить scripts/orchestration/project_init.py или .ps1).
- Новый агент = роль в пайплайне (11_AGENT_ROLES) + его артефакты в artifacts/ проекта — без изменения общей структуры.
- Новый тип артефакта = расширение шаблона (10 §9) с версионированием.

## 6. АУДИТ И РЕВЬЮ МЕХАНИЗМА (обязательно)
При внедрении (после полной сборки фабрики, в рамках B5/приёмки) провести:
- АУДИТ (code-auditor): единообразие правил/переменных между проектами, отсутствие коллизий артефактов, соблюдение шаблонов (10 §9), рантайм не в git.
- РЕВЬЮ (code-reviewer): критическая оценка структуры на масштабируемость (10 проектов, 30 агентов, 1000 артефактов), имена/пути, конфликты.
- Результат: отчёт + правки контрактов (если нужно) + регистрация новых TD.
