# 13_FACTORY_CYCLE.md — Единый цикл фабрики (запуск через оркестратора, минимум ручных операций)
**Дата:** 2026-10-07 · **Статус:** АКТИВЕН · **Версия:** 1.0

## 1. ЦЕЛЬ
Фабрика работает как ЕДИНЫЙ ЦИКЛ: оркестратор запускает блок → цепочка звеньев выполняется автоматически → результат деплоится. Минимум ручных операций (в идеале: одна команда на блок).

## 2. ПОТОК (что происходит автоматически)
1. ПОЛЬЗОВАТЕЛЬ: «запусти блок X» (или оркестратор по трекеру).
2. ОРКЕСТРАТОР:
   - определяет блок (X), читает его спеку (01/02/03)
   - диспатчит ВОРКЕРА (контракт 06 §3.1 + спека цитатой + состояние файлов)
   - получает worker JSON → диспатчит РЕВЬЮЕРА (спека + worker + 05/07/10)
   - получает вердикт → диспатчит АУДИТОРА (вердикт ревьюера + артефакты + 05/07/10)
   - при APPROVE → АНАЛИТИК (сводка + вопросы) → РЕСЕРЧЕР (ответы) → ДЕПЛОЕР (коммит+push+контроль цикла)
   - при REQUEST_CHANGES → возврат воркеру с объединённым списком правок (цикл повторяется, максимум N=3 итераций → эскалация пользователю)
3. После деплоя: обновить трекер (todowrite), журнал (ANALYST_REPORTS), ORCHESTRATOR_NOTES.

## 3. СПОСОБЫ ДИСПАТЧА (все ведут в единый цикл)
| Способ | Команда/триггер | Автоматизация |
|---|---|---|
| A) Интерактивный | пользователь пишет «запусти B1-T5» | оркестратор ведёт цепочку сам |
| B) Headless run | `opencode run --agent code-orchestrator "запусти блок X"` | цепочка идёт в одной headless-сессии |
| C) Скрипт-цикл | `factory_cycle.py --block X` (предложить) | полностью автоматический диспатч звеньев по контрактам |
| D) CI (GitHub Actions) | push в feature-ветку → тесты/приёмка | частично (позже, W11/W12) |

Рекомендация: вариант C (скрипт-оркестратор) как целевой — один вызов, минимум ручных операций. Сейчас работает вариант A (оркестратор-LLM ведёт вручную). Скрипт-оркестратор = TODO (TD).

**Режим аудитора (контракт 14):** диспетчер (оркестратор/runner) при каждом запуске аудитора ОБЯЗАН указать в промпте ПЕРВОЙ строкой `РЕЖИМ: A` (in-cycle) или `РЕЖИМ: B` (standalone) — по контракту 14 (`14_AUDITOR_MODES.md`). Сырой стандартный контракт аудитору давать НЕЛЬЗЯ (шаблон с обязательным полем режима). Внешний аудит (документация, черновики, НД, книги Excel) — ВСЕГДА режим B: пути к аудируемым артефактам допустимы, вердикта ревьюера нет, аудит выполняется по существу. Если режим не указан — аудитор запрашивает уточнение A/B, а не мечется (14 §3).

## 4. КОНТРАКТ ОРКЕСТРАТОРА ПРИ ЗАПУСКЕ (минимум операций)
При получении «запусти блок X» оркестратор выполняет (по чек-листу):
1. Базлайн-сверка: трекер + ANALYST_REPORTS + git log → подтвердить, что предусловия блока готовы.
2. Прочитать спеку блока (01/02/03) + актуальный PROBLEMS_REGISTER (TD, влияющие на блок).
3. Диспатчить звенья ПОСЛЕДОВАТЕЛЬНО (06 §2), каждый раз прикладывая: контракты (05/07/10/11), спеку цитатой, артефакты предыдущего звена, «материал для работы».
4. Промежуточные вердикты: REQUEST_CHANGES → вернуть воркеру (макс 3 итерации), APPROVE → дальше.
5. Деплой: только после APPROVE всех звеньев; деплоер по 04 (включая контроль TD 3.6).
6. Финал: обновить трекер, журнал, заметки. Отчёт пользователю: что сделано, TD, следующий блок.

**Правило P2 (обязательный деплой):** 3×APPROVE без коммита = блок НЕ закрыт. Деплой обязателен после APPROVE (контракт 04). Артефакты проекта — в git (контракт 12). Блок считается закрытым ТОЛЬКО после деплоя.

**При E2E-тестах оркестратор подключает observer-режим (20): якорь базовой задачи, self-check, детекторы D1-D9.** E2E/приёмочный прогон — основной триггер observer (§3.3 контракта 20): тестовый контекст просачивается в контекст разработки harness, агент забывает, что тестирует (прецедент gost13132). По контракту 20 оркестратор при запуске E2E: (1) проверяет/создаёт якорь `projects/<PID>/contracts/base-task-capsule.md` (20 §3.1), (2) подключает observer-режим роутера (20 §3.3), (3) требует observer_<ID>.json при длинных цепочках (≥120 шагов) и при срабатывании любого детектора D1-D9 (20 §3.5).

**После цикла — прогон E-детекторов (21).** По контракту 21 (энтропийный контур, `21_ENTROPY_CONTOUR.md`) оркестратор в чек-лист финала цикла добавляет прогон E-детекторов косяков исполнения (E1-E10, 21 §4 — расширение D1-D9 из 20): не запустил поиск, не использовал тул, поискал но не применил, декларативный отчёт без verified_by_commands (P4), нет промежуточных проверок, дублирование руками, не зафиксировал TD (05), нет кодового арбитра, ложная готовность (DoD PASS без теста), бесконечный/вырожденный вывод (E10). Смотритель (ExternalAuditorV2, режим B по 14) бросает находки в корзину `.runs/entropy/bucket.json`, обновитель (td_updater) за монетки превращает их в TD/исправления (21 §3/§5/§6). Начисления монеток/штрафов — ТОЛЬКО кодом (21 §6, ноль «LLM судит LLM»). При исчерпании бюджета звена (шаги/токены/контекст/рекурсия) оркестратор требует от звена вернуть `[LIMIT]` + partial-результат, НЕ продолжать генерацию (21 §8; критерий остановки — TD-DEV-56).

## 4.5. ПЕРИОДИЧЕСКАЯ СВЕРКА БАЗЛАЙНА (аудитором)
**Правило:** каждые 3-5 итераций фабрики (или после каждых ~5-8 запушенных коммитов / по объёму работы: новый блок B/W/EXP) оркестратор ОБЯЗАН запускать СВЕРКУ БАЗЛАЙНА аудитором (code-auditor).

### Что сверяет аудитор (по контракту базлайн-аудита):
1. Git-история: запушенные коммиты vs трекер (todowrite) — все ли блоки закрыты, ничего ли не потеряно.
2. Журнал ANALYST_REPORTS.md: каждая строка блока = коммит (нет ли потерь строк, как было с W7).
3. PROBLEMS_REGISTER: все ли TD зарегистрированы, нет ли TD-рекомендаций без регистрации.
4. Контракты docs/CODERS/: все ли tracked в git (не untracked).
5. Push-блокеры: не накопились ли (хуки W1).
6. TD-блокеры: что мешает следующему шагу.

### Триггеры (запускать досрочно, если):
- Потеря артефакта/журнала обнаружена
- Push заблокирован
- Смена ветки/структуры
- Подозрение на потерю данных

### Выход сверки:
- Отчёт аудитора: auditor_baseline_check_<N>.json
- Обновлённый трекер
- Список разрывов + рекомендации

## 5. ЧТО УЖЕ АВТОМАТИЗИРОВАНО vs РУЧНОЕ
| Операция | Сейчас | Цель |

| Деплой | деплоер руками | по контракту 04 |
| Трекер | руками оркестратора | factory_cycle.py обновляет |
