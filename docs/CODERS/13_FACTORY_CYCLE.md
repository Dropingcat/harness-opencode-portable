# 13_FACTORY_CYCLE.md — Единый цикл фабрики (запуск через оркестратора, минимум ручных операций)
**Дата:** 2026-10-07 · **Статус:** АКТИВЕН · **Версия:** 1.0

## 1. ЦЕЛЬ
Фабрика работает как ЕДИНЫЙ ЦИКЛ: оркестратор запускает блок → цепочка звеньев выполняется автоматически → результат деплоится. Минимум ручных операций (в идеале: одна команда на блок).

## 2. ПОТОК (что происходит автоматически)
1. ПОЛЬЗОВАТЕЛЬ: «запусти блок X» (или оркестратор по трекеру).
2. ОРКЕСТРАТОР:
   - определяет блок (X), читает его спеку (01/02/03)
   - диспатчит ВОРКЕРА (контракт 06 §3.1 + спека цитатой + состояние файлов)
   - получает worker JSON → диспатчит РЕВЬЮЕРА (спека + worker + 05/07/10)
   - получает вердикт → диспатчит АУДИТОРА (вердикт ревьюера + артефакты + 05/07/10)
   - при APPROVE → АНАЛИТИК (сводка + вопросы) → РЕСЕРЧЕР (ответы) → ДЕПЛОЕР (коммит+push+контроль цикла)
   - при REQUEST_CHANGES → возврат воркеру с объединённым списком правок (цикл повторяется, максимум N=3 итераций → эскалация пользователю)
3. После деплоя: обновить трекер (todowrite), журнал (ANALYST_REPORTS), ORCHESTRATOR_NOTES.

## 3. СПОСОБЫ ДИСПАТЧА (все ведут в единый цикл)
| Способ | Команда/триггер | Автоматизация |
|---|---|---|
| A) Интерактивный | пользователь пишет «запусти B1-T5» | оркестратор ведёт цепочку сам |
| B) Headless run | `opencode run --agent code-orchestrator "запусти блок X"` | цепочка идёт в одной headless-сессии |
| C) Скрипт-цикл | `factory_cycle.py --block X` (предложить) | полностью автоматический диспатч звеньев по контрактам |
| D) CI (GitHub Actions) | push в feature-ветку → тесты/приёмка | частично (позже, W11/W12) |

Рекомендация: вариант C (скрипт-оркестратор) как целевой — один вызов, минимум ручных операций. Сейчас работает вариант A (оркестратор-LLM ведёт вручную). Скрипт-оркестратор = TODO (TD).

## 4. КОНТРАКТ ОРКЕСТРАТОРА ПРИ ЗАПУСКЕ (минимум операций)
При получении «запусти блок X» оркестратор выполняет (по чек-листу):
1. Базлайн-сверка: трекер + ANALYST_REPORTS + git log → подтвердить, что предусловия блока готовы.
2. Прочитать спеку блока (01/02/03) + актуальный PROBLEMS_REGISTER (TD, влияющие на блок).
3. Диспатчить звенья ПОСЛЕДОВАТЕЛЬНО (06 §2), каждый раз прикладывая: контракты (05/07/10/11), спеку цитатой, артефакты предыдущего звена, «материал для работы».
4. Промежуточные вердикты: REQUEST_CHANGES → вернуть воркеру (макс 3 итерации), APPROVE → дальше.
5. Деплой: только после APPROVE всех звеньев; деплоер по 04 (включая контроль TD 3.6).
6. Финал: обновить трекер, журнал, заметки. Отчёт пользователю: что сделано, TD, следующий блок.

## 5. ЧТО УЖЕ АВТОМАТИЗИРОВАНО vs РУЧНОЕ
| Операция | Сейчас | Цель |
|---|---|---|
| Диспатч звеньев | руками оркестратора (промпт каждому) | скрипт factory_cycle.py (или шаблоны промптов) |
| Артефакты | вручную сохраняются | шаблон ${HARNESS_ROOT}/<ROLE>_<BLOCK_ID>.json (10 §9) |
| TD-регистрация | звенья (иногда) | автоматическая проверка деплоера (04 §3.6) |
| Деплой | деплоер руками | по контракту 04 |
| Трекер | руками оркестратора | factory_cycle.py обновляет |
