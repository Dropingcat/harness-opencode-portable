# 16_RESEARCH_MINI_FACTORY.md — Мини-фабрика глубокого исследования (внутри цикла ресерчера)
**Дата:** 2026-10-07 · **Статус:** АКТИВЕН · **Версия:** 1.0

## 1. НАЗНАЧЕНИЕ
Полноценный ресерчер в пайплайне (analyst → researcher → deployer) для задач глубокого исследования:
- внешне-научный канал (источники, НД, статьи) — через research-orchestrator BRICKS-runner;
- код/БД/легаси/git — через general-ядро;
- ТРИЗ-ветка — разрешение противоречий по workspace-методике;
- внешний аудитор (режим B, 14) — контроль качества исследования;
- ЛАЙТ-вариант — быстрый ресерчер без полного цикла.

## 2. ДВА РЕЖИМА РЕСЕРЧЕРА

### РЕЖИМ DEEP (полная мини-фабрика)
Когда: задача требует внешних источников/НД/статей + верификации фактов + глубокого анализа.
Цепочка:
1. АНАЛИТИК формулирует вопросы (10 §4).
2. РЕСЕРЧЕР (general-ядро) решает: нужен ли внешний канал (10 §5).
   - ДА → запускает research-orchestrator (через `opencode run --agent research-orchestrator` или runner-обёртки, TD-099) с ResearchTask-контрактом.
   - research-orchestrator гонит BRICKS-runner (claim-parser → source-fetcher → fact-checker → numeric → post → tribunal → synthesize) — детерминированный слой.
   - НЕТ → general-ядро копает код/БД/легаси/git.
3. ВНЕШНИЙ АУДИТОР (режим B, 14): аудит результата исследования ПО СУЩЕСТВУ (объект=findings, критерии=вопросы аналитика+НД) → вердикт.
4. ТРИЗ-ветка: если найдены противоречия (конфликт источников, несовместимые требования) — применить triz-problem-solving (противоречие → приём → решение), по workspace-методике.
5. РЕСЕРЧЕР сводит всё в researcher_<ID>.json (findings с доказательствами).
6. ДЕПЛОЕР коммитит.

### РЕЖИМ LIGHT (быстрый лайт-ресерчер)
Когда: вопрос локальный (код/БД/легаси), внешние источники не нужны, время важно.
Цепочка: аналитик → general-ресерчер (только ядро: read/grep/sqlite/git, verify) → ответ с доказательствами → деплоер.
Без: research-orchestrator, внешнего аудитора, ТРИЗ-ветки.
Порог: оркестратор решает по типу вопроса (внешние факты → DEEP; локальный код → LIGHT).

## 3. РОЛЬ РОУТЕРА
- Роутер (`coder_run` / `harness_run`) определяет контур задачи: исследование vs код vs письмо.
- Внутри ресерчера: роутер помогает решить DEEP vs LIGHT (по признакам: нужны ли внешние источники/НД).
- runtime_snapshot.json — источник правды маршрутов (W5).

## 4. ВНЕШНИЙ АУДИТОР В ЦИКЛЕ (детализация по 14 B)
- Внешний аудитор (code-auditor, РЕЖИМ: B) подключается как ОТДЕЛЬНОЕ звено после ресерчера (до деплоера) для глубоких исследований:
  - Вход: объект (findings ресерчера, sources, verdicts), критерии (вопросы аналитика, НД, ГОСТы), PROBLEMS_REGISTER.
  - Проверяет: полноту ответов на вопросы аналитика, корректность цитирования/trust, отсутствие двойного счёта, соответствие НД.
  - Выход: вердикт APPROVE/REQUEST_CHANGES/REJECT + находки 09 + TD (05).
- Когда подключать: DEEP-режим (обязательно), LIGHT-режим (опционально, по решению оркестратора).

## 5. ТРИЗ-ВЕТКА (по workspace-методике)
- Источник: `E:\Documents\Документы\workspace\агент кодер\агент кодер\лид-триз.md`, `ариз агент\методичка.md`, скил `triz-problem-solving`.
- Применение: при противоречии в исследовании (источники спорят, требования несовместимы):
  1. Сформулировать противоречие (improving × worsening параметры).
  2. Применить ТРИЗ-приёмы (#1 Дробление, #5 Объединение, #22 Обратить вред, #26 Копирование).
  3. Зафиксировать решение (что разрешили, каким приёмом).
  4. ИКР (идеальный конечный результат) — без запрещённых глаголов.
- Выход: секция «ТРИЗ-резолюции» в researcher_<ID>.json.

## 6. ДИНАМИЧЕСКИЕ КОНТРАКТЫ (по типу задачи)
- ResearchTask-контракт (вход для research-orchestrator): {question, claims/text, criteria (НД), expected_output, max_cost, mode: deep|light}.
- Контракт ресерчера формируется оркестратором динамически: DEEP (вкл. внешний аудит+ТРИЗ) или LIGHT (без них).

## 8. ПОРЯДОК ЗАПУСКА (для оркестратора)
1. Вопрос аналитика → оркестратор классифицирует DEEP/LIGHT.
2. LIGHT: general-ресерчер (ядро) → researcher_<ID>.json.
3. DEEP: general-ресерчер (ядро + запуск research-orchestrator) → BRICKS → findings → внешний аудитор (B) → ТРИЗ (если противоречия) → researcher_<ID>.json.
4. Деплоер коммитит + контроль TD.
