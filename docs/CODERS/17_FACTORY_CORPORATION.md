# 17_FACTORY_CORPORATION.md — Фабрика как корпорация разработки (масштабирование)
**Дата:** 2026-10-11 · **Статус:** АКТИВЕН · **Версия:** 1.0

## 1. МЕТАФОРА
Фабрика = «Корпорация разработки ПО». Все контракты 00-16 — это внутренние регламенты компании.
- Заказчик (клиент/бизнес) — внешний интерфейс: формулирует потребность, принимает результат, даёт обратную связь.
- Оркестратор = PM/директор отдела: ведёт заказчика, формирует циклы, управляет командами (субагентами).
- Субагенты = отделы: аналитика (synthesizer/analyst), исследования (researcher+research-orchestrator), разработка (coder-worker), QA (reviewer/tester/auditor), деплой (deployer).

## 2. РОЛИ В КОРПОРАЦИИ (маппинг на контракты)
| Корпоративная роль | Агент/контракт |
|---|---|
| Заказчик | Пользователь (внешний интерфейс) |
| PM/директор | code-orchestrator / writing-orchestrator / research-orchestrator (13, 15) |
| Аналитический отдел | analyst = synthesizer (11), claim-parser |
| Отдел исследований | researcher = general + research-orchestrator (16 DEEP/LIGHT) |
| Отдел разработки | coder-worker (06 §3.1) |
| QA/контроль | code-reviewer, code-tester, code-auditor (06 §3.2/3.3, 14 A/B) |
| DevOps/деплой | deployer = general (04) |
| Бюро стандартов | контракты 00-16 (регламенты), ORCHESTRATOR_NOTES (уроки) |

## 3. ЦИКЛ ВЗАИМОДЕЙСТВИЯ С ЗАКАЗЧИКОМ (оркестратор = PM)
### Стадии (SDLC, адаптировано):
1. **DISCOVERY (черновик)** — интервью с заказчиком (вопросник, interview-me-стиль), сбор потребности, контекст, границы. Выход: черновик ТЗ.
2. **PLANNING (планирование)** — анализ (analyst), исследование (researcher DEEP/LIGHT), ТЗ + план + вехи + оценка (контракты 08/16). Выход: план с вехами, риски, DoD.
3. **PILOT (пилот/MVP)** — цикл фабрики на пилотном объёме: worker→reviewer→auditor→deployer (06), демо заказчику. Выход: работающий пилот + отчёт.
4. **PRODUCTION (прод)** — полный цикл, приёмка (03 матрёшка M0-M6, E2E), документация, поддержка (мета-цикл W7, сны W13). Выход: прод-релиз.

### Контракт PM с заказчиком (на каждой стадии):
- **Вход от заказчика:** потребность/боль, критерии приёмки, ограничения (бюджет, сроки), контекст.
- **Выход PM заказчику:** вехи, демо (пилот), отчёт о статусе, вопросы (когда нужны решения), принятая версия.
- **Правила:**
  - Приёмка ТОЛЬКО по DoD (фальсифицируемые критерии, 03), не по «нравится/не нравится».
  - Обратная связь заказчика → в следующий цикл (ANALYST_REPORTS, ORCHESTRATOR_NOTES).
  - Каждая стадия = отдельный цикл фабрики (13): черновик → ревью → аудит → деплой (в артефакты проекта).
  - Решения заказчика (RUD-стиль) — REQUIRES_USER_DECISION с дефолтами (как в B1-T5).

## 4. ЦИКЛЫ РАЗРАБОТКИ (стадийные)
| Стадия | Вход | Цикл фабрики | Выход |
|---|---|---|---|
| Черновик | потребность | интервью → analyst (ТЗ-черновик) | черновик ТЗ |
| План | черновик ТЗ | analyst + researcher → план/вехи | план + DoD |
| Пилот | план | worker→reviewer→auditor→deployer (06) | MVP + демо |
| Прод | пилот | полный цикл + матрёшка (03) + доки | прод-релиз |

**Входные сценарии (уровни L0–L4) → карта пайплайнов (18).** PM определяет уровень входа по триггерам 18 §4 (glob/Test-Path: L0 концепт-текст → P3, L1 наработки → P2/P3, L2 доки → P2, L3 код без доков → P2, L4 готовый код → P1) и запускает нужный пайплайн из карты 18 §3 (динамический контракт — 18 §5). Каждая стадия DISCOVERY/PLANNING/PILOT/PRODUCTION реализуется пайплайном из карты 18 (P3 для плана, P1 для пилота/прода); вход проекта ниже L2 → обязательная предфаза по 18, а не прямой диспатч в цикл.
