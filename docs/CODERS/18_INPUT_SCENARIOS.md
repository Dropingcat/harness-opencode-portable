# 18_INPUT_SCENARIOS.md — Карта входных сценариев → динамические пайплайны
**Дата:** 2026-10-11 · **Статус:** АКТИВЕН · **Версия:** 1.0

## 1. НАЗНАЧЕНИЕ
Оркестратор (PM, 17) получает вход РАЗНОГО уровня (от идеи до готового кода). Этот контракт — карта: уровень входа → какой пайплайн запустить, с динамическим контрактом. Никакой философии: определил уровень → запусти нужный пайплайн.

## 2. УРОВНИ ВХОДА (таблица)
| Уровень | Что это | Признаки (как определить) | Что достроить | Мин. пайплайн |
|---|---|---|---|---|
| L0 | Концепт-текст | только текст, glob пуст, нет файлов | интервью (17 §3), исследование | P3 |
| L1 | Комплект наработок | файлы есть, нет ТЗ/структуры | систематизация (08), реверс | P2/P3 |
| L2 | Готовая документация | ТЗ/спеки/архитектура есть | план реализации | P2 |
| L3 | Базовые скрипты | код есть, документации нет | аудит B (14), документация | P2 |
| L4 | Готовый код | код+тесты+доки | (ничего) | P1 (после PLANNING) |

## 3. ПАЙПЛАЙНЫ (таблица)
| Пайплайн | Вход | Цепочка | Контракт | Выход | DoD | Когда |
|---|---|---|---|---|---|---|
| P1 Классический | L3/L4 после PLANNING | worker→reviewer→auditor→deployer (06) | контракт 06 | код/фиксы | DoD 06 | вход кодируемый, ТЗ есть |
| P2 Исследование+план→цикл | L0/L1/L3 | analyst→researcher→auditor B→planner→P1 | 08/10/16 | ТЗ+план+код | DoD+план принят | нужно достроить ТЗ |
| P3 Планировочный | L0/L1 | analyser→researcher→planner→auditor→deployer | 08/10/16 | план+ТЗ+оценка (НЕ код) | DoD плана | концепт/наработки |
| P4 Корпоративный | любой | стадии 17 (DISCOVERY→PLANNING→PILOT→PRODUCTION) | 17+все | прод-релиз | матрёшка 03 | полный проект |
| P5 Лайт | мелкий вопрос | LIGHT ресерчер + точечный цикл | 16 LIGHT | быстрый ответ | ответ дан | мелкое |

## 4. ТРИГГЕРЫ ВЫБОРА (для оркестратора)
Формула (проверяй по порядку):
1. Только текст, файлов нет → **L0 → P3**
2. Файлы есть, нет ТЗ → **L1 → P2/P3** (если много наработок — P3, если среднее — P2)
3. ТЗ/спеки есть, кода нет → **L2 → P2**
4. Код есть, доки нет → **L3 → P2**
5. Код+тесты+доки → **L4 → P1** (если план уже принят) или P4 (полный проект)
6. Мелкий вопрос/фикс → **P5**

## 5. ДИНАМИЧЕСКИЕ КОНТРАКТЫ (шаблоны по 15 §2)
Общий каркас по 15 §2: `Ты — РУКИ ОРКЕСТРАТОРА (general-исполнитель). Выполни задачу по контракту. Не думай о решениях — всё предрешено.` Переменные {{TASK}}/{{PATHS}}/{{REQUIREMENTS}}/{{STEPS}}/{{RESULT}}/{{ARTIFACT_PATH}}/{{SCOPE}} подставляет оркестратор (15 §3). Аудитору — `РЕЖИМ: A`/`РЕЖИМ: B` первой строкой (14 §3, R9).

### P1 — Контракт классического цикла (блок)
- `{{TASK}}`: реализовать блок `{{BLOCK_ID}}` по спеке ({{PATHS}} — секция из 01/02/03 цитатой); скрытых решений нет.
- `{{REQUIREMENTS}}`: DoD блока дословно (03); контракты 05/07/09/10/11 (06 §3); материал — артефакты предыдущего звена накопительно (10 §1).
- `{{STEPS}}`: worker (06 §3.1) → reviewer (06 §3.2) → auditor **РЕЖИМ: A** (14 §2A); при APPROVE×2 → analyst (08 §4) → researcher (08 §5, 16 LIGHT/DEEP) → deployer (04). Ограничение сокращённого P1 (без аналитика/ресерчера) — см. §6.
- `{{RESULT}}`: вердикты + артефакты `{{ARTIFACT_PATH}}` = `${HARNESS_ROOT}/<ROLE>_<BLOCK_ID>.json` (10 §9).
- `{{SCOPE}}`: блок 01/02/03; REQUEST_CHANGES → возврат воркеру, макс 3 итерации (13 §2); не коммитить (деплоер 04); спеки прикладывать цитатой, не ссылкой (06 §4.5).

### P2 — Контракт предфазы «исследование+аудит входа» (→ P1)
- `{{TASK}}`: провести предварительное исследование и аудит входного состояния (уровень `{{INPUT_LEVEL}}`: L0/L1/L3), сформировать ТЗ-план; затем запустить P1 по сформированным блокам.
- `{{REQUIREMENTS}}`: систематизировать вход (analyst, 10 §4), исследовать контекст/референсы (researcher 16 DEEP/LIGHT), аудит входного состояния **РЕЖИМ: B** (14 §2B), ТЗ-план+вехи+DoD (17 §4).
- `{{STEPS}}`: analyst (08 §4) → researcher (16: DEEP если внешние источники/НД, иначе LIGHT) → auditor **РЕЖИМ: B** (14 §2B, объект = вход) → planner (= analyst+researcher, 17 §4) → фиксация артефактов входа в `projects/<PID>/artifacts/` (12, R8) → P1.
- `{{RESULT}}`: ТЗ-план + зафиксированное состояние входа + вердикт аудитора B → выход P1.
- `{{SCOPE}}`: НЕ додумывать ТЗ — при недостатке входа вернуть на L0/L1 → P3 (08 §1 п.5); НЕ запускать P1 до вердикта аудитора B.

### P3 — Контракт планировочного пайплайна (выход = план, НЕ код)
- `{{TASK}}`: сформировать план работ + ТЗ + вехи + риски + оценку для входа (`{{INPUT_LEVEL}}`: L0/L1 / потребность заказчика). Реализацию НЕ выполнять.
- `{{REQUIREMENTS}}`: ТЗ-черновик (analyst), исследование недостающего (researcher 16), план+вехи+оценка (17 §4), аудит плана **РЕЖИМ: B** (14 §2B), DoD плана (03).
- `{{STEPS}}`: analyst = synthesizer (11 §3) → researcher (16) → planner (= analyst+researcher, 17 §4 — пара, НЕ новое звено, R4) → auditor **РЕЖИМ: B** (14 §2B, объект = план/ТЗ) → deployer (04: коммит плана в `projects/<PID>/reports/`, 12) → приёмка заказчиком/PM по DoD (17 §3).
- `{{RESULT}}`: план+ТЗ+вехи+риски+оценка в `projects/<PID>/reports/` — НЕ код.
- `{{SCOPE}}`: НЕ писать код; НЕ запускать P1 по плану без вердикта аудитора B и без приёмки заказчика (17 §3); решения заказчика — REQUIRES_USER_DECISION с дефолтами.

### P4 — Контракт PM с заказчиком (стадийный, 17 §3 + композиция пайплайнов)
- `{{TASK}}`: вести проект заказчика по стадиям 17: DISCOVERY → PLANNING → PILOT → PRODUCTION. Каждая стадия = свой пайплайн (P3 для плана, P1 для пилота/прода).
- `{{REQUIREMENTS}}`: контракт PM (17 §3) — вход (потребность/критерии приёмки/ограничения/контекст), выход (вехи/демо/отчёт/вопросы/принятая версия); приёмка ТОЛЬКО по DoD (03), не «нравится».
- `{{STEPS}}`: 1) DISCOVERY: интервью (17 §3) → analyst (ТЗ-черновик) → auditor B (аудит черновика ТЗ); 2) PLANNING = P3 (→ план+DoD); 3) PILOT = P1 на пилотном объёме + демо заказчику; 4) PRODUCTION = полный P1 + матрёшка M0-M6 (03) + доки + поддержка (W7/W13).
- `{{RESULT}}`: статус стадии, вехи, демо, принятая версия, отчёт заказчику.
- `{{SCOPE}}`: НЕ перескакивать стадии (PILOT без PLANNING-плана запрещён); модель — пользовательский выбор, НЕ хардкод (урок 3.8).

### P5 — Контракт лайт-вопроса/фикса
- `{{TASK}}`: ответить на вопрос / точечный фикс (`{{INPUT_LEVEL}}`: L0/L1-вопрос или L4-фикс). Полный конвейер НЕ нужен.
- `{{REQUIREMENTS}}`: researcher LIGHT (16 §2 LIGHT: general-ядро, read/grep/sqlite/git + verify), внешние факты/НД → эскалация на DEEP (16 §2, R6).
- `{{STEPS}}`: researcher LIGHT (16) → ответ с доказательствами (pass/fail/not-tested); при фиксе — мини-цикл worker → reviewer (06 §3.1/3.2) → deployer (04).
- `{{RESULT}}`: ответ с доказательствами / принятый фикс; «находок не было» — явная пометка (09 §4).
- `{{SCOPE}}`: фикс не выходит за `{{SCOPE}}` (15 §2); не гнать полный конвейер 06 (перерасход).

## 6. ПРАВИЛА И ГРАНИЦЫ
- planner = пара analyst+researcher (17 §4), НЕ новое звено (R4).
- Сокращённый P1 без аналитика/ресерчера — ТОЛЬКО после PLANNING (иначе теряется контекст — R3); критерий: аналитик/ресерчер в P1 запускаются, если блок затрагивает интеграцию/смежные блоки (06 §3.3), иначе решение оркестратора с пометкой в отчёте.
- Смешанный вход → разделить на контуры (код/доки/исследование) и обрабатывать каждый своим пайплайном (R1).
- Большой план → эшелонирование по вехам (17), не одной порцией (R2).
- Аудитор: A (in-cycle) для звеньев P1, B (standalone) для входного аудита/плана (P2-предфаза, P3, P4-черновик) — §5, первой строкой `РЕЖИМ: A/B` (14 §3, R9).
- L0 → обязательное интервью (17 §3 DISCOVERY); L1/L3 → обязательная фиксация входных артефактов в `projects/<PID>/artifacts/` до планирования (12, R8).
- Пайплайны = композиции существующих звеньев (06/08/16/17/15), НЕ новые агенты.
