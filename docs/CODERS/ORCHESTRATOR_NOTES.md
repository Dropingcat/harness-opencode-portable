## 3. СВОДНЫЕ УРОКИ (накопительно)

### 3.1 Кириллица и PowerShell 5.1
- `.Replace` искажает «Документы»; inline PS-команды с кириллицей ломаются.
- Воркеры уже научились править Python-скриптом (TD-DEV-1), но контракт инструмент не закрепляет → закрепить в 06 §3.1.

### 3.2 Ложные PASS ревьюеров
- TD-DEV-7 (DoD), TD-DEV-18 (артефакты freeze) — PASS по заявлению воркера без Test-Path.
- 07 §3.3 «не верь отчётам» появился ПОСЛЕ TD-DEV-7, но паттерн повторился → усилить требование Test-Path каждого заявленного артефакта.

### 3.3 TD-регистрация звеньями
- Воркеры (TD-DEV-14/24), ресерчер (TD-DEV-20/21/26) рекомендовали TD, но не писали в реестр.
- Деплоер/оркестратор закрывали постфактум. Контракт 05 требует, но соблюдение слабое → обязательная регистрация в ТОМ ЖЕ прогоне.

### 3.4 Спеки и числа
- Спека «27 py» vs 28 (TD-DEV-23) — писались в сессии, не сверялись с FS → сверять количество файлов с FS (glob) перед передачей воркеру.

### 3.5 Последовательность и фокус ролей
- Параллельный ревьюер/аудитор привёл к ожиданию вердикта (B1-T2) → перешли на последовательность (06).
- Ревьюер фокусируется на блоке, аудитор — на системе: двойной источник правды (TD-DEV-13) нашёл аудитор, не ревьюер.

### 3.6 Что работает — закрепить
- Контроль цикла 3.6 деплоером (поймал TD-DEV-26, TD-DEV-37).
- Черновик промпта ресерчеру от аналитика (экономит контекст).
- Селективный add деплоера без мусора (4 раза подряд).
- Ресерчеры с доказательствами (команды/файлы:строки), критичное сверх вопросов (N1: --once не пишет saved_at).

### 3.7 Блокирующий хук: гонять ЦЕЛИКОМ до и после регенерации
- TD-DEV-37: stub-gate (coder-dom-verify.sh:32) блокирует push на stubs в чужих файлах, но ревьюер/аудитор видели только STALE (TD-DEV-31) — хук падал раньше, до stub-gate не доходил.
- Урок: pre-push проверять ДО и ПОСЛЕ регенерации (STALE маскирует нижние проверки). Деплоер — последнее звено, реально гоняющее хук целиком; вскрытые блокировки регистрировать как TD.

### 3.8 Модель = пользовательский выбор, НЕ хардкод (EXP-1b)
- Агенты воевали с провайдером: arise monarch (claude-opus-4-5) против проектного polza. Причина: глобальный config НЕ содержит model; claude-opus-4-5 — дефолт плагина `@bluelovers/opencode-arise` (SHADOW_AGENTS.monarch.model); arise ставит default_agent=monarch, его модель выигрывает при отсутствии явного выбора (проектный polza лишь fallback).
- Вывод D «глобальный > portable» ФАЛЬСИФИЦИРОВАН аудитором: EXP-1b прошёл на polza только потому что `-m` передан явно.
- Урок: контракты должны указывать «используй `OPENCODE_MODEL` если задана, иначе — дефолт opencode»; модель выбирает пользователь (UI / `-m` / переменная), НЕ фиксировать провайдера в контрактах/скриптах.

### 3.9 Артефакт-путь по шаблону (EXP-1b)
- Аудитор записал `auditor_EXP-1b.json` в workspace без явного пути — косяк контракта: шаблон не был закреплён.
- Урок: введён шаблон `${HARNESS_ROOT}/<ROLE>_<BLOCK_ID>.json` (HARNESS_ROOT = E:\opencode_harness_portable, НЕ `.runs/` — рантайм, не версионируется). Закреплён в контрактах 04/05/06/08/10/11 + CONFIG_MERGE.md. Отчёт в отчёте: путь указывать явно.

### 3.10 Масштабирование: директория артефактов проекта (контракт-фикс 3)
- Сейчас всё живёт в одном корне (`E:\opencode_harness_portable`), артефакты — `${HARNESS_ROOT}/<ROLE>_<BLOCK_ID>.json`. При старте НОВОГО проекта (клиент, модуль, исследование) это даст коллизии имён и смешение артефактов разных проектов.
- Урок: при старте нового проекта — отдельная директория артефактов (`${HARNESS_ROOT}/projects/<PROJECT_ID>/` с `artifacts/`, `runs/`, `reports/`, `config.env`), единообразные правила/переменные/верификация — `12_PROJECT_ARTIFACTS.md`. Аудит+ревью самого механизма — обязателен при внедрении (после полной сборки фабрики, B5/приёмка).

### 3.11 Единый цикл фабрики (контракт 13)
- Единый цикл фабрики формализован (`13_FACTORY_CYCLE.md`): оркестратор запускает блок → цепочка звеньев автоматически → деплой; минимум ручных операций. Цель — одна команда на блок.
- Сейчас оркестратор вручную пишет промпт каждому звену (вариант A диспатча). Целевой способ — вариант C (скрипт-оркестратор `factory_cycle.py`), зафиксирован как TD-DEV-41 (после B5, шаблоны промптов из контрактов 04/05/06/08/10/11, тест на 2 блоках).
- Урок: при каждом запуске блока оркестратор работает по чек-листу 13 §4 (базлайн-сверка → спека блока + PROBLEMS_REGISTER → последовательный диспатч 06 §2 с артефактами предыдущего звена → вердикты с итерациями (макс 3) → деплой по 04 → финал: трекер/журнал/заметки).
