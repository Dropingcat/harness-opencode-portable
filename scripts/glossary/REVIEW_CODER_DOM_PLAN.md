## 2. Слабые места (по компонентам)

### S1. Рёбра CALLS (A4) — НЕ определён формат и точность
- **Проблема**: план говорит «PyCG/pyan3», но нет: (а) как нормализовать рёбра (функция→функция vs модуль→функция), (б) как мержить 2 генератора, (в) что делать с динамическими вызовами/декораторами/вложенными функциями (PyCG слабо покрывает).
- **Риск**: рёбра CALLS будут неполными/ложными → граф «кажется верным», но дезинформирует.
- **Вопрос ресёрчу**: практика нормализации call-graph в YAML для функций; известные лимиты PyCG/pyan3 на декораторах; альтернативы (tree-sitter + собственная сборка).

### S2. Stub-детекция (A5) — Protocol-детект неполон
- **Проблема**: детектор «класс наследует Protocol → interface» ловит не всё: (а) ABC с `@abstractmethod`, (б) `typing.Protocol` через `isinstance`, (в) функции с `raise NotImplementedError`, (г) stub-маркеры (`# stub:`, `# TODO: implement`).
- **Вопрос ресёрчу**: как vulture/dead/semgrep отличают интерфейсы от заглушек; стандартные маркеры; radon-пороги CC для stub.

### S3. Схема coder_dom (B1) — нет JSON Schema и миграции
- **Проблема**: `coder-dom/1.0` описан YAML-примером, но нет машинной схемы (JSON Schema), нет политики unknown-fields, нет миграции 1.0→1.1.
- **Вопрос ресёрчу**: практика версионирования YAML-контрактов (как Structurizr/OpenAPI/AsyncAPI), JSON Schema для YAML, миграции.

### S4. Verify-гейт (B4) — производительность и стабильность
- **Проблема**: перегенерация всего дерева на каждый коммит (197 модулей) медленная; diff нестабилен (порядок, timestamps).
- **Вопрос ресёрчу**: pre-commit инкрементальные перегенерации; стабильные diff (canonical JSON); кэш по source_hash.

### S5. G-ownership (C1) — конфликт при параллельной разработке
- **Проблема**: «не пересекаясь по строкам» — но функция может вызывать другую; изменение сигнатуры ломает вызывающих. Ownership не защищает от такого.
- **Вопрос ресёрчу**: практика code ownership (CODEOWNERS, GitHub), dependency-aware assignment, merge-конфликты при смене API.

### S6. Интеграция со спекой semantic_field (E1) — огромный объём
- **Проблема**: 87-секционная спека — это целый научный слой (InformationUnit, RTT, QuestionGraph, Hypothesis lifecycle). План не декомпозировал её на реализуемые шаги с бюджетами.
- **Вопрос ресёрчу**: существует ли готовый пакет (research_semantics) или части (RTT-валидаторы, claim-graph) — чтобы не писать с нуля.

### S7. Пустые функции (TD-078) — 23 шт, классификация не завершена
- **Проблема**: инвентаризация дала 23, но классификация Protocol-vs-stub сделана только для ports.py (18 — Protocol) и tribunal_role_runtime (1 — stub). Остальные 4 (capsules.run, r0/ids ×2, tribunal_live_dialogue.invoke) не проверены.
- **Вопрос ресёрчу**: (факт, локальный) — проверить эти 4 вручную; (ресёрч) — как крупные проекты трекают stubs как debt (issue-трекеры, маркеры).

### S8. Параллельные сессии / перезапись — процессный риск
- **Проблема**: уже терялись TD-073/075 при параллельной перезаписи tech_debt.json.
- **Вопрос**: нужен lock/merge-протокол для config/tech_debt.json (или раздельные файлы на контур).
