## 1. Цели и границы ответственности
**Цель:** Реализовать исполнительные агенты (Coder, Critic) в виде **заглушек (Stubs)** и **адаптеров**, строго следующих контрактам из WP-0. Обеспечить возможность замены заглушек на LLM без изменения кода оркестратора.  
**Границы:**
*   ✅ **Входит:** CoderStub, CriticStub, FixNotesAdapter, интерфейсы агентов, базовые промт-шаблоны (как константы).
*   ❌ **Не входит:** Реальные вызовы LLM API (это WP-3), оркестрация цикла (WP-1), верификация кода (WP-4).

> ⚠️ **Критическое ограничение:** Заглушки должны быть **детерминированными**. Никаких случайных значений, никаких внешних зависимостей. Поведение должно полностью определяться входными данными для воспроизводимости тестов.

## 3. Детальные требования к компонентам

### 3.1. Coder Stub (`coder_stub.py`)
Детерминированная имитация кодера для тестирования оркестратора.

**Требования:**
1.  Класс `CoderStub`, реализующий протокол `Agent` (или Callable).
2.  Метод `generate(spec: str, context: Dict, fix_notes: List[FixNote]) -> Artifact`.
3.  **Поведение определяется ключевыми словами в `spec`:**
    *   Содержит `"sum"` / `"сумма"` → возвращает корректную функцию суммы.
    *   Содержит `"error"` / `"ошибка"` → возвращает код с синтаксической ошибкой.
    *   Содержит `"lazy"` / `"лень"` → возвращает артефакт с минимальными изменениями (только комментарий).
    *   Содержит `"hack"` / `"хак"` → возвращает артефакт с измененным тестом (если тест есть в контексте).
    *   По умолчанию → возвращает пустой артефакт с `reasoning="No matching keyword"`.
4.  **Обработка `fix_notes`:**
    *   Если `fix_notes` не пуст и содержит `"syntax"` → следующий вызов возвращает исправленный код.
    *   Игнорирует остальные типы fix_notes (для простоты стаба).
5.  Возвращаемый `Artifact` должен строго соответствовать схеме из WP-0.
6.  Время выполнения < 1ms.

**⚠️ Контроль ошибок:**
*   Стаб НЕ должен читать файлы из диска. Все данные берутся из `context` или хардкода.
*   Стаб НЕ должен модифицировать входные параметры.

### 3.2. Critic Stub (`critic_stub.py`)
Детерминированная имитация холодного критика.

**Требования:**
1.  Класс `CriticStub`, реализующий протокол `Agent`.
2.  Метод `evaluate(artifact: Artifact, tool_results: Dict) -> CriticReport`.
3.  **Поведение определяется содержимым `artifact.files` и `tool_results`:**
    *   Если `tool_results` содержит ключ `"error"` или `"traceback"` → `Verdict.FAIL` + finding с severity=BLOCKING.
    *   Если `artifact.files` содержит строку `"TODO"` или `"pass"` → `Verdict.FAIL` + finding с severity=WARNING.
    *   Если `artifact.files` пуст → `Verdict.AMBIGUOUS` + `requires_user=True` + вопрос "Empty artifact".
    *   Если все проверки пройдены → `Verdict.PASS`.
4.  **Холодность:** Метод НЕ принимает историю, trace, предыдущие отчеты. Только текущий артефакт и результаты инструментов.
5.  `uncertainty_score` вычисляется детерминированно:
    *   PASS → 0.0
    *   FAIL → 0.2
    *   AMBIGUOUS → 0.8
6.  Строгое соответствие схеме `CriticReport` из WP-0.

**⚠️ Контроль ошибок:**
*   Критик НЕ должен пытаться парсить код (AST). Только текстовый поиск и проверка tool_results.
*   Критик НЕ должен предлагать исправления в `findings.problem`. Только описание проблемы.

### 3.3. Fix Notes Adapter (`fix_notes_adapter.py`)
Преобразует сырые findings критика в структурированный вход для кодера.

**Требования:**
1.  Функция `adapt_findings(findings: List[Finding]) -> List[FixNote]`.
2.  Фильтрация: убирает `severity=NIT` (опционально, конфигурируемо).
3.  Сортировка: BLOCKING > WARNING.
4.  Форматирование: создает человекочитаемое описание для LLM/стаба.
    *   Пример: `[BLOCKING] main.py:10 - Unhandled exception in parse_input()`
5.  Дедупликация: если одна и та же проблема встречается несколько раз, объединяет в одну запись с счетчиком.
6.  Возвращает список объектов `FixNote` (модель из WP-0).

**Почему это важно:** Кодер (особенно LLM) плохо понимает сырые JSON-структуры. Адаптер создает "мостик" между формальным отчетом и естественным языком/структурированным списком.

### 3.4. Промт-шаблоны (`prompts/`)
Подготовка для WP-3. Не используются в рантайме WP-2, но должны быть созданы сейчас.

**Требования:**
1.  Текстовые файлы с плейсхолдерами `{spec}`, `{context}`, `{fix_notes}`.
2.  Включают **жесткие инструкции по формату вывода** (JSON Schema reference).
3.  Включают **anti-instructions**: "Do not modify tests", "Do not add comments explaining obvious code".
4.  Версионируются вместе с кодом.

## 4. Критерии приемки (Definition of Done)

### 4.1. Функциональные
- [ ] CoderStub возвращает валидные артефакты для всех 5 сценариев.
- [ ] CriticStub корректно реагирует на ошибки в tool_results и содержимое артефакта.
- [ ] FixNotesAdapter дедуплицирует и сортирует findings.
- [ ] Все заглушки работают без внешних зависимостей и сети.
- [ ] Поведение заглушек полностью воспроизводимо при одинаковых входах.

### 4.2. Тестовые
- [ ] Unit-тесты для каждого сценария стабов (≥ 15 тестов суммарно).
- [ ] Тесты на граничные случаи: пустой spec, пустой artifact, malformed tool_results.
- [ ] Тесты на соответствие схемам WP-0 (валидация через Pydantic).
- [ ] Property-based тесты для FixNotesAdapter (любой валидный список findings → валидный список fix_notes).

### 4.3. Интеграционные (предварительные)
- [ ] CoderStub + CriticStub + FixNotesAdapter образуют замкнутый цикл из 3 итераций без падений.
- [ ] Цикл завершается по одному из stop-criteria (PASS или LIMIT).

### 4.4. Структурные
- [ ] Нет импортов `openai`, `anthropic`, `requests`.
- [ ] Все классы имеют docstrings с примерами использования.
- [ ] Type hints полные, mypy strict passes.
- [ ] Промт-шаблоны лежат в `src/agents/prompts/`.

## 5. Риски и митигации

| Риск | Вероятность | Влияние | Митигация |
| :--- | :--- | :--- | :--- |
| Стабы слишком умные и скрывают баги оркестратора | Высокая | Ложное чувство безопасности | Стабы должны быть *глупыми*. Только keyword matching. Никакой эвристики. |
| Несовпадение схем с WP-0 | Средняя | Runtime errors | Автоматическая валидация в тестах. CI check на соответствие schema.json. |
| FixNotesAdapter теряет информацию | Средняя | Кодер не может исправить ошибку | Тесты на round-trip: findings → fix_notes → (проверка полноты). |
| Промт-шаблоны устаревают | Низкая | WP-3 потребует переписывания | Шаблоны версионируются. Изменения только через PR. |
| Заглушки зависят от порядка вызовов | Средняя | Невоспроизводимость | Стабы stateless. Любое состояние передается явно через аргументы. |

## 8. Чек-лист для ревьюера

- [ ] **Stateless:** У стабов нет `self.state`, `self.history`, глобальных переменных.
- [ ] **Deterministic:** При одинаковых входах результат идентичен бит-в-бит.
- [ ] **Schema Compliance:** Все return values валидируются через модели WP-0.
- [ ] **No External Deps:** Нет сетевых вызовов, чтения файлов вне context.
- [ ] **FixNotes Quality:** Адаптер не теряет severity, file, line.
- [ ] **Prompts Exist:** Шаблоны созданы и содержат JSON-schema instructions.
