# АРИЗ/ТРИЗ АНАЛИЗ ПРОЕКТА «КИРПИЧИК»
**Дата:** 2024-01-15
**Автор:** Tech Lead
**Статус:** Approved

## 1. Идеальный Конечный Результат (ИКР)

### ИКР-1 (Функциональный)
Система сама продвигает задачу вперёд, автоматически выявляет имитацию прогресса, локально исправляет ошибки, и только при реальной неоднозначности привлекает пользователя; при этом контроль не увеличивает сложность сильнее, чем прирост качества.

### ИКР-2 (Безопасностный)
Система сама предотвращает выполнение вредоносного кода и утечку ресурсов, не требуя внешнего контроля за пределами sandbox.

### Анти-ИКР (Запреты)
- Система НИКОГДА не должна выдавать DONE без реального результата
- Контролёр НИКОГДА не должен менять артефакт
- Аудитор НИКОГДА не должен оценивать качество кода
- Критик НИКОГДА не должен видеть reasoning кодера или историю итераций
- Система НИКОГДА не должна выполнять код без изоляции

## 2. Операционная зона и Конфликты

| # | Конфликт | Сторона А | Сторона Б | Приоритет |
|---|----------|-----------|-----------|-----------|
| 1 | Контроль vs Сложность | Нужны проверки (аудитор) | Проверки раздувают систему | High |
| 2 | Перезапуск vs Зацикливание | Оркестратор перезапускает | Risk бесконечного repair loop | High |
| 3 | Аудит vs Продуктивность | Аудитор ищет обходы | Аудитор блокирует работу | Medium |
| 4 | Канбан vs Реальность | Статусы отражают прогресс | Workflow ради workflow | Medium |

## 3. Разрешение противоречий

| Противоречие | ТРИЗ-приём | Архитектурное решение | Обоснование |
|--------------|------------|------------------------|-------------|
| Контроль vs Сложность | Разделение | Критик (результат) и Аудитор (процесс) разделены во времени и пространстве | Разные зоны ответственности, исключают пересечение |
| Быстро vs Качественно | Предварительное действие | Pre-computed metrics, Policy Engine до вызова LLM | Детерминированные метрики не требуют LLM |
| Изоляция vs Производительность | Динамичность | Local sandbox (dev), Docker (prod) | Разные режимы для разных сред |
| Частый аудит vs Нагрузка | Переход в новое измерение | Триггерный аудит вместо циклического | Аудитор вызывается только при условиях |
| Детальный лог vs Объём | Матрёшка | TraceEntry хранит хэш, полный артефакт отдельно | Предотвращает раздувание трассы |

## 4. Использование ресурсов

| Ресурс | Использование | Экономия |
|--------|---------------|----------|
| Логи оркестратора | Источник для ProcessMetrics | Не нужен отдельный мониторинг-агент |
| Diff артефактов | Индикатор прогресса/лени | Не нужен AST-анализ в аудиторе |
| Статусы канбана | Триггеры для аудитора | Не нужен отдельный scheduler |
| Ошибки верификатора | Вход для критика | Не нужен повторный парсинг |
| История fix_notes | Детектор осцилляции | Не нужна сложная ML-модель |

## 5. Валидация (Анти-ИКР тест)

- [x] Имитация прогресса невозможна — есть ≥2 независимых механизма верификации (критик + аудитор)
- [x] Бюрократическая экспансия невозможна — контролёр не имеет права менять артефакт
- [x] Смешение ролей невозможно — контракты исключают пересечение полей (CriticReport vs AuditReport)
- [x] Зависимость от LLM устранена — stub mode работает, все stop-criteria детерминированы
- [x] Утечка доверия невозможна — Threat Model покрыта митигациями

## 6. Театральность (проверка на лишние компоненты)

| Компонент | Если убрать, ИКР нарушится? | Вердикт |
|-----------|----------------------------|---------|
| Orchestrator | Да — нет управления циклом | Оставить |
| Coder | Да — нет генерации артефактов | Оставить |
| Critic | Да — нет оценки результата | Оставить |
| Auditor | Да — нет контроля процесса | Оставить |
| Verifier | Да — нет проверки в sandbox | Оставить |
| Kanban/State Machine | Да — нет управления статусами | Оставить |

Лишних компонентов не обнаружено. Все элементы архитектуры функционально необходимы.
