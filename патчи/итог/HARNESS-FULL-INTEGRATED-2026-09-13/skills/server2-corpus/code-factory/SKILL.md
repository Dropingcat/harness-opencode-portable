# Code Factory — вызов фабрики кода

## Overview

Фабрика кода — мультиагентная система для автономной разработки. Оркестратор (я) декомпозирует задачу на модули, параллельно диспатчит воркеров/ревьюеров/тестеров через `task`, контролирует качество, при конфликте вызывает аудитора.

## Провайдеры (проверено)

| Субагент | Модель | Провайдер | Статус |
|---|---|---|---|
| `coder-worker` | `deepseek-v4-flash:cloud` | ollama-cloud | ✅ работает |
| `code-reviewer` | `deepseek-v4-flash:cloud` | ollama-cloud | ✅ работает |
| `code-tester` | `deepseek-v4-flash:cloud` | ollama-cloud | ✅ работает |
| `code-auditor` | `glm-5.2` | ollama-cloud | ✅ настроен |
| `experimenter` | `glm-5.2` | ollama-cloud | ✅ primary |

- Главная модель opencode: `ollama-cloud/glm-5.2`
- Ключ ollama-cloud: в `~/.config/opencode/opencode.jsonc`
- **Субагенты запускаются ТОЛЬКО через `task`** (`opencode run --agent <subagent>` не работает — "subagent, not a primary agent")

## Когда использовать

- Задача разбивается на независимые модули (параллельная разработка)
- Нужно ревью кода (code-reviewer)
- Нужно тестирование (code-tester)
- Конфликт воркер↔ревьюер (2+ раунда) → code-auditor
- Оптимизация (experimenter + autoresearch)

## Как запустить

### 1. Декомпозиция
Разбей задачу на модули с зависимостями. Определи для каждого: тип, сложность, объём, воркера.

### 2. Параллельный диспатч (task)
Каждый воркер получает контракт:
```
goal: [что сделать]
context: [пути, интерфейс, требования]
output: [что вернуть]
acceptance: [критерии приёмки]
```

Пример:
```
task(subagent_type="coder-worker", prompt="goal: ... context: ... output: ... acceptance: ...")
```

### 3. Ревью (параллельно)
Диспатч `code-reviewer` на каждый модуль. Каждое замечание — конкретно (файл:строка, проблема, предложение).

### 4. Тестирование
Диспатч `code-tester`. Тесты реально запускаются.

### 5. Трибунал (при конфликте)
Если воркер и ревьюер не сошлись (2+ раунда) → `code-auditor` (передай метаданные процесса, НЕ код).

### 6. Интеграция
Собери модули, проверь целостность, верни отчёт.

## Контракты делегирования

### Воркер (coder-worker)
```
goal: Напиши модуль [X] по спецификации
context: Пути, интерфейс, требования, зависимости
output: JSON {module, code, description, notes}
acceptance: Код компилируется, соответствует интерфейсу, JSON валиден
```

### Ревьюер (code-reviewer)
```
goal: Проверь код модуля [X]
context: Путь к коду, спецификация, требования
output: JSON {module, verdict, comments[]} — каждый comment с falsification
acceptance: Каждое замечание конкретно и фальсифицируемо, JSON валиден
```

### Тестер (code-tester)
```
goal: Напиши и запусти тесты для модуля [X]
context: Путь к коду, спецификация
output: JSON {module, result, passed, failed, coverage, tests[], problems[]}
acceptance: Тесты реально запускаются, JSON валиден
```

### Аудитор (code-auditor)
```
goal: Вынеси финальный вердикт по конфликту воркера и ревьюера
context: Метаданные процесса (вердикты, ответы, iteration_count), НЕ код
output: JSON {verdict, justification, process_analysis}
acceptance: Вердикт учитывает обе стороны, JSON валиден
```

## Правила

1. **LLM свидетельствует, КОД решает** — факты жёстко, стиль свободно.
2. **Честный резак** — нет данных → не выдумываем.
3. **Сходимость через трибунал** — качество решает дискуссия.
4. **Всегда тестируй** — код без тестов не принимается.
5. **Фальсифицируемость** — каждое замечание ревьюера опровержимо.
6. **Аудитор не читает код** — только метаданные процесса.

## Stop criteria (детерминизм)

- `verdict = APPROVE` → DONE
- `requires_user = True` → BLOCKED (эскалация)
- `iteration_limit` (3-5) → BLOCKED
- `auditor_block` → BLOCKED

## Pitfalls

- ❌ Не запускать субагентов через `opencode run --agent` — только через `task`
- ❌ Не передавать код аудитору — только метаданные
- ❌ Не принимать невалидный JSON от воркера/ревьюера
- ❌ Не вымучивать результат после 3+ раундов — честно сообщить
