# Architecture Review — Self-Learning Academic Writer (SLAW)

> Ревью v1 (2026-09-03). Оцениваю: что упущено, что упрощено, что берут с GitHub, какие наши идеи усилить.

---

## 1. Что в архитектуре сильно (не трогаем)

1. **Единая парадигма вложенных клаймов** (уровни 0-4) — сильное объединение «текста» и «данных». Мало кто это делает.
2. **Провенанс и рецензирование per-unit** — превосходит «git для документа» (git не знает claims).
3. **Локальное обучение на корпусе** (M3) — без облака, с извлечением клайм-графов и паттернов связанности.
4. **Сравнение через таблицу клаймов + граф связанности** (M4) — детерминированная функция, не LLM-«ощущение».
5. **Двусторонний конвейер (sieve)** — просеять на входе, собрать лучшее на выходе.
6. **YAML как канон + SQLite как индекс** — doc-as-code, diffable, валидируемо.

## 2. Что УПУЩЕНО (добавить в архитектуру)

### 2.1 Отсутствует явный «Feedback Loop» (обучение по результатам)
- После сборки документа и его (реальной) оценки/цитирования — обратная связь в корпус: что сработало, что нет.
- **Усиление**: M3 должен включать «post-hoc learning»: черновик → внешняя оценка → обновление паттернов.

### 2.2 Нет «нормализации клайм-графов» перед сравнением
- Разные эталоны имеют разную гранулярность (кто-то дробит тезисы, кто-то нет).
- **Усиление**: ввести **claim-graph alignment** (нормализация до общего разрешения) перед M4.

### 2.3 Нет «мультиязычности»/«двуязычности» (рус/англ)
- Академический текст может требовать билингвальности (аннотации EN, термины).
- **Усиление**: добавить в genre registry «language: ru|en|bilingual», стилевые профили отдельно.

### 2.4 Нет «воспроизводимости эксперимента» (для исследования)
- Мы — исследователи; нужен **experiment log**: какой клайм-граф, какие параметры, какая метрика.
- **Усиление**: M3/M4 должны писать метаданные эксперимента (как MLflow/Weights&Biases, но локально, в YAML).

### 2.5 Нет «conflict resolution» между claims при сборке
- Sieve отмечает конфликты (ConflictBuilder), но **нет правила выбора** при конфликте двух strong claims.
- **Усиление**: добавить в M4 «conflict arbitration» (по доверию evidence, свежести, релевантности).

### 2.6 Нет «стилевого аватара» (личный профиль автора)
- Пользователь хочет «свой стиль» или стиль конкретного журнала/ВАК.
- **Усиление**: Style Profile должен включать «author persona» (целевой профиль, а не только эталонный).

### 2.7 Нет «оценки сложности/объёма» (budget)
- Диссертация 150 стр. vs. longread 2000 слов — нужна **бюджетная модель** (token/word/странчный план).

## 3. Что УПРОЩЕНО (требует углубления)

### 3.1 «Паттерны связанности» — слишком абстрактно
- «claim → 3 evidence → conclusion» — хорошо, но **как извлекать автоматически**?
- **Усиление**: формализовать как **подграфы-мотивы** (graph motifs) + поиск повторяющихся (subgraph mining, gSpan/GRAMI-like). Это конкретный алгоритм, не «идея».

### 3.2 «Сравнение графов» — нужен конкретный алгоритм
- Graph Edit Distance / WL-kernel — упомянуто, но не зафиксировано.
- **Усиление**: зафиксировать метрики: WL-subtree kernel, Graph Edit Distance (GED), пороги (thresholds).

### 3.3 «Локальный векторный индекс» — не указан движок
- **Усиление**: зафиксировать: `sentence-transformers` (BGE-m3) + `sqlite-vec`/`faiss` (CPU), batching, кэш.

### 3.4 «Стилевой профиль» — «статистический» без деталей
- **Усиление**: точный список: длины предложений, dependency depth, лексика (TF-IDF/word2vec), структурные маркеры, ГОСТ-чеки, читаемость (Flesch-Кинкейд для EN / адаптир. для RU).

## 4. Что уже используют на GitHub (идеи, которые берём/усиливаем)

### 4.1 Doc-as-code / тексты как код
- **docops-hq/learnapidoc-ru** — doc-as-code инструменты (Markdown+Git+SSG). Берём принцип, усиляем: **клайм-граф вместо файла**.
- **asciidoctor/asciidoctor** — документы как код, семантические роли. Идея: семантические роли юнитов (у нас `role:` уже есть — усилить).
- **ttscoff/MarkdownExperiments** — продвинутый Markdown. Не критично.

### 4.2 Клайм-графы / научная структура
- **anthropics/scientific-benchmarking** (Claude) — claim-графы и проверка фактов. Идея: **claim-level validation** (у нас уже есть в researcher-core).
- **cmu-phil/evidence-mark** (проверка claims) — идея: **оценка силы evidence**, перенести в ranking.
- **datamasking/claim-verification** — паттерны верификации claims. Идея: **сигнатуры сомнительных claims**.

### 4.3 Самообучение / retrieval
- **facebookresearch/faiss** — векторный индекс (CPU, локально). Берём как движок M3.
- **UKPLab/sentence-transformers** — embeddings (BGE-m3 для RU). Берём.
- **huggingface/transformers** — если нужны локальные LLM для извлечения claims. Опционально.

### 4.4 Текст как граф / структура
- **TextGraphs** (ACL-семинар) — текст как граф. Идея: **graph-of-text** — мы делаем глубже (клайм-уровни).
- **nlp-graph/connection** — связанность. Идея: **переходы как граф**.

## 5. Какие НАШИ идеи развить сильнее

### 5.1 «Копирование подходов, не только стиля»
- Развить: **схемы связанности как first-class объекты** (не просто паттерны, а «рецепты»: когда использовать, как адаптировать).
- Аргументационные схемы (Toulmin-модель) — «claim → data → warrant → backing → qualifier → rebuttal». Это **усилит** наш claim-graph: добавляем роль юнита в аргументации.

### 5.2 «Сравнение через граф связанности»
- Развить: **не только изоморфизм, а семантическое выравнивание** — перенос «скелета связанности» эталона на новый контент.
- Формализовать: **graph template transfer** (как в нейро-символьных системах).

### 5.3 «Таблица клаймов»
- Развить: **таблица клаймов = интерфейс** (не только метрика). Человек-рецензент видит её, отмечает «этот тезис слабый» → система учится.

### 5.4 «Sieve» (двусторонний конвейер)
- Развить: **стохастический sieve** — на выходе не всегда «лучший», иногда «второй лучший» (для разнообразия), как beam-search с температурой.
